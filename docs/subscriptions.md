# Подписки, Caddy и первые клиенты

## Что показывает обнаружение

`check` читает SQLite выбранной панели в режиме `mode=ro` / `query_only`:
inbound, protocol/transport/security, listener, состояние, число и имена
клиентов, наличие ID подписки. В отчёт не входят UUID, пароли, ID подписок,
приватные ключи REALITY и исходные JSON настроек. Ограничены объём JSON,
число inbound (100) и число отображаемых клиентов (200). Неподдерживаемая
схема помечается как непрочитанная, а не как пустая панель.

`doctor` отдельно проверяет HTTP подписок с хоста, HTTP из сетевого
пространства Caddy, публикацию HTTPS-порта, маршрут в Caddyfile и HTTPS по
домену с обычной проверкой сертификата. Если есть включённый клиент с subId,
проверяется его настоящая выдача: ожидается HTTP 200. Иначе используется
несуществующий ID: HTTP 404 подтверждает только доступ к HTTP-серверу.
Ответы, URL с ID и содержимое подписок не сохраняются в журнал.

Проверка HTTPS идёт с VPS; внешний доступ с компьютера/телефона и VPN-трафик
нуждаются в отдельной проверке. HTTP 502 в браузере при работающей админке
не означает, что надо заново выполнять Fresh.

Перед новым Fresh на свободном будущем порту подписок временно запускается
HTTP-ответчик, и Caddy обращается к нему из своего сетевого пространства.
При включённом управлении UFW перед этой пробой добавляется узкое разрешение
bridge → host. Если HTTP всё равно недоступен, установка останавливается
до создания каталога ноды и изменения общего Caddy, а изменения UFW откатываются.
После запуска проверяется уже настоящий HTTP-сервер подписок.

## Первый inbound и клиент

В параметрах установки добавь VLESS/REALITY inbound, свободный порт, SNI,
listener и имя первого клиента. Для выхода через SSH listener — 127.0.0.1;
для прямого подключения клиентов — 0.0.0.0. Порты 443/80, занятые Caddy,
нельзя одновременно отдавать Xray на пересекающихся адресах. Например,
для нового inbound можно выбрать свободный 8443.

Fresh создаёт inbound и первого клиента через локальный API фиксированной
3x-ui 3.11.0. UUID, REALITY keys, short ID и subId создаются на VPS. Клиент
получает включённую подписку, имя по форме или `nodekit-<имя inbound>`.
`subscriptions.json` (600) в каталоге ноды содержит приватные ссылки;
`tunnel-connections.json` (600) — параметры подключения. Эти файлы не
экспортируются в обычный отчёт. При Restore клиенты и ID берутся из бэкапа;
этот список не создаёт новые inbound.

## Уже установленная панель: домен, порт, новые inbound

1. Обнови обнаружение. Открой параметры ноды, укажи домен, публичный
   HTTPS-порт, внутренний порт подписок и нужные новые inbound.
2. Сохрани параметры. Это пока только локальная конфигурация Nodekit.
3. Открой **Операции → Подписки и inbound**, проверь план и запусти его.
4. Повтори диагностику и проверь полную ссылку подписки с компьютера.

Операция `configure` поддерживает только активную панель Nodekit с общим
Caddy. Панель и Xray кратковременно перезапускаются: активные VPN-соединения
могут прерваться. Требуются исходный manifest и точный сохранённый `Caddyfile.site`.
Нельзя одновременно менять runtime, образ, админский endpoint/путь, путь
подписок или SSH-туннели: для этого нужна миграция. Повторное создание
контейнера Caddy допускается только при явно выбранном новом экземпляре,
содержащем неизменённый сохранённый сайт этой ноды.

До изменений проверяется Caddyfile против активной конфигурации и отсутствие
чужого маршрута для нового домена. Затем создаётся SQLite snapshot в закрытом
каталоге ноды, кратковременно останавливается только панель, меняются настройки
подписок и панель запускается снова. Доступ от Caddy проверяется **до** изменения
общего сайта. Заменяется только точный сохранённый фрагмент; остальной Caddyfile,
сети сохраняются. Публикации согласуются отдельно при включённой автоматике.
Существующие inbound/клиенты не редактируются.
Ранее созданные Nodekit inbound с теми же параметрами пропускаются; конфликт
с чужим inbound вызывает отказ. При сбое восстанавливаются прежние настройки
и сайт; удаляются только inbound, созданные этой операцией. Ошибка отката
выводится отдельно. Новые настройки TLS/DNS проверяются после применения,
результаты видны в отчёте; ACME может завершиться позже самой операции.

## Пример адреса `https://sub.example.com:2096/sub/<ID>` с общим Docker Caddy

`sub.example.com` и `203.0.113.10` — учебные значения; замените их
собственным доменом и IP перед выполнением команд.

2096 — **публичный порт Caddy**. Внутренний HTTP-порт подписок 3x-ui может
оставаться 2097. Смена одной ссылки/настройки 3x-ui не публикует порт Docker.

Найди Compose общего Caddy:

```bash
sudo docker inspect shared-caddy --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}'
sudo docker inspect shared-caddy --format '{{ index .Config.Labels "com.docker.compose.project.config_files" }}'
sudo docker inspect shared-caddy --format '{{ index .Config.Labels "com.docker.compose.service" }}'
```

В **его** Compose добавь к существующим публикациям сервиса Caddy:

```yaml
ports:
  - "80:80"
  - "443:443/tcp"
  - "443:443/udp"
  - "2096:2096/tcp"
```

Сохрани остальные параметры и публикации, проверь `docker compose config` и
обнови только этот сервис через `docker compose up -d --no-deps <service>`
из правильного проекта с его исходными `-f`/env-параметрами. Изменение ports
пересоздаёт контейнер: будет короткое прерывание всех сайтов общего Caddy.
Теперь Nodekit может выполнить это через минимальный Compose override,
если включено согласование портов и исходный проект совпадает с работающим
контейнером. Подробности и ограничения: [управление сетью](network-management.md).
Firewall провайдера по-прежнему проверяется отдельно.

После этого повтори обнаружение в Nodekit, явно выбери текущий shared-caddy,
задай домен `sub.example.com`, HTTPS-порт 2096 и примени операцию `configure`.
Требуется публикация с одинаковыми номерами `2096:2096`; Nodekit не угадывает
внешний порт при произвольном remapping. Получение/продление сертификата
текущего шаблона использует HTTP-01 на 80; публичный HTTPS может быть на 2096.

```powershell
Test-NetConnection 203.0.113.10 -Port 2096
curl.exe -I https://sub.example.com:2096/
```

404 корневого пути ожидаем; ошибка сертификата — нет. Настоящую подписку
проверяй GET-запросом по приватной ссылке клиента, не публикуя её в журнале.

## Локализация 502 для bridge → host

Для gateway/порта со снимка установки:

```bash
curl -sv --max-time 5 http://172.30.50.1:2097/sub/nodekit-check -o /dev/null
sudo docker exec shared-caddy wget -S -T 5 -O /dev/null http://172.30.50.1:2097/sub/nodekit-check
sudo ss -ltnp '( sport = :2097 )'
sudo docker logs --since 5m shared-caddy
```

HTTP 404/ошибка неизвестного ID — нормальны для этого проверочного адреса.
Если хост отвечает, а Caddy ловит timeout, проверь firewall для трафика
Docker bridge → host. Если обе стороны получают connection refused,
проверь фактический listener и журнал панели. Отсутствие встроенного TLS
подписок в 3x-ui нормально, когда TLS завершает Caddy.

Для UFW узнай фактические subnet, gateway и имя bridge:

```bash
sudo docker network inspect shared-proxy
ip -br address
sudo ufw status verbose
```

При подтверждённой блокировке разрешай только bridge/subnet Caddy → нужный
gateway и внутренний TCP-порт подписок. Пример (замени interface и subnet
фактическими, не применяй при другом firewall):

```bash
sudo ufw allow in on br-XXXXXXXXXXXX proto tcp from 172.30.50.0/24 to 172.30.50.1 port 2097 comment 'nodekit-ultra-subscriptions'
```

Не открывай 2097 всему интернету и не меняй subListen на 0.0.0.0 для обхода
проблемы. При включённом управлении UFW Nodekit добавляет такое узкое правило
автоматически после обнаружения фактического bridge. Изменение указано в плане.

## Подключение Caddy после установки панели

Если панель была установлена с `deployment.caddy_mode: none` или `docker`,
одного выбора `existing` в локальном YAML недостаточно: на VPS остаётся исходный
manifest, а `Caddyfile.site` ещё не создан.

1. В параметрах развёртывания выбери **существующий Caddy**, домен и порт
   **подписок**, сохрани настройки. HTTPS-домен будущего XHTTP должен отличаться
   от домена подписок.
2. На вкладке **Inbound → Обновить** получи актуальный отчёт. Если подключение
   ещё не применено, появится кнопка **Подключить Caddy**. Та же операция доступна
   в разделе **Операции → Подключить Caddy**.
3. Проверь план и запусти операцию. Она сохраняет SQLite snapshot, перезапускает
   только выбранную панель для настройки backend подписок, проверяет доступ
   из Caddy и применяет сайт. Исходные runtime, образ, админский endpoint,
   путь подписок и SSH-туннели должны совпадать с manifest.
4. После успешного подключения обнови обнаружение и создай **VLESS / XHTTP**.
   При редактировании параметров существующих подписок используй обычную
   операцию **Подписки и inbound**.

Для выбранного общего Caddy проверяются файл против активной конфигурации,
коллизии доменов, bridge/bind, UFW и публикации портов. Добавляется только сайт
этой ноды. Сторонние сайты и контейнеры не заменяются. При выборе другого Caddy
ранее установленный отдельный Caddy автоматически не удаляется; конфликтующие
домены или занятые порты потребуют отдельного решения.

Можно выбрать **исходный Docker Caddy этой же ноды**. Его файл должен точно
совпадать с конфигурацией, созданной из исходного manifest; требуются исходные
Docker project/service labels, образ и host network. Nodekit сохранит исходный
файл, включит admin API только на `127.0.0.1:2019` и кратковременно перезапустит
только этот контейнер. Порт 2019 должен быть свободен; наружу он не открывается.
После перехода дальнейшие изменения применяются обычным `caddy reload`.
Изменённый вручную файл или чужой контейнер автоматически не присваиваются.

При ошибке восстанавливаются настройки подписок, собственный сайт и записанные
операцией metadata. Клиенты, UUID, subId и существующие inbound сохраняются;
новые REALITY inbound из параметров развёртывания при подключении Caddy
не создаются. Их можно применить отдельно через **Подписки и inbound**.
Переустановка 3x-ui, ручное редактирование manifest и повторный Fresh не нужны.

XHTTP использует публичный `443/tcp` независимо от порта подписок. При создании
Nodekit добавляет управляемое UFW-разрешение на 443, сохраняя приватный backend.
Для Caddy в bridge-сети требуется публикация `443:443/tcp`; её отсутствие
останавливает операцию до создания inbound. Для Caddy на хосте проверяется,
что 443 уже принадлежит его маршрутам либо свободен для нового HTTPS listener.
