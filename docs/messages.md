# Каталоги сообщений и общие компоненты

## Backend

Все собственные ошибки, сообщения диагностики/развёртывания, тексты плана и системных логов
собраны в `backend/src/framework/messages`. Каталог не зависит от app, FastAPI или Pydantic
и входит в stdlib bundle удалённого агента.

| Файл | Назначение |
| --- | --- |
| `codes.py` | `ErrorCode` — стабильные категории ошибок API; `MessageKey` — ключи текстов |
| `definitions.py` | Неизменяемый словарь шаблонов |
| `catalog.py` | `MessageCatalog`, проверка параметров и функция `text` |
| `__init__.py` | Публичные импорты |

```python
from framework.entities import ConflictError
from framework.messages import MessageKey, text as message_text

message = message_text(MessageKey.PORT_OCCUPIED, port=2096)
raise ConflictError(message)
```

Используй именованные параметры: меняется словарь, а не десятки f-строк.
Существующие сообщения остались на английском, чтобы сохранить читаемость старых журналов
и текущий контракт. Динамическое переключение языка сейчас не реализовано.

Для нового текста:

1. Добавь ключ в `MessageKey` и шаблон в `MESSAGES`.
2. Обращайся через `text(...)`; если рядом есть переменная `text`, используй alias
   `message_text`, как в примере.
3. Передай ровно нужные параметры. Пропущенный/лишний параметр — ошибка программирования,
   каталог не оставляет необработанные `{placeholder}` в пользовательском сообщении.
4. Для ошибки выбери подходящий существующий класс исключения. Его `ErrorCode` не зависит
   от словесной формулировки. Новый machine code нужен, только если меняется различаемая
   клиентом категория ошибки.

Общий каталог неизменяем. Отдельный `MessageCatalog` можно создать со своим словарём;
это не изменяет глобальные шаблоны. В параметры не передавай пароли или полные тела
запросов. Сторонний stderr и причины сетевых ошибок могут остаться динамическими данными:
их текст не является ещё одним справочником сообщений приложения.

Старые строковые значения `error.code` сохранены. Формат API `{ok, data, error, meta}`
и формат журналов не менялись. Из-за стандартного `StrEnum` агент требует Python 3.11+;
до импорта bundle выполняется проверка версии.

## Frontend

`frontend/src/framework` содержит переиспользуемую часть интерфейса:

- `api`: общий клиент, проверку envelope, `ApiError`, стабильные `ErrorCode` и
  `getErrorMessage`. Сбой сети имеет собственный код, отмена запроса сохраняет AbortError.
- `messages`: системные уведомления, подтверждения, подписи операций/статусов и интерфейса;
  `formatMessage` проверяет именованные параметры, `statusLabel` обрабатывает неизвестные статусы.
- `components`: Button, IconButton, Alert, CardHeader, Spinner, StatusBadge и их базовые стили.

```tsx
import { Button, Alert } from './framework/components';
import { messages } from './framework/messages';

<Button loading={busy} onClick={save}>{messages.ui.save}</Button>
<Alert tone="success">{messages.notice.configSaved}</Alert>
```

Общие компоненты не импортируют App, типы нод или бизнес-состояние. Кнопка по умолчанию
имеет `type="button"`, при загрузке блокируется; уведомления имеют role alert/status,
а IconButton требует доступное имя. Базовые стили подключены перед стилями приложения,
чтобы его layout и правило reduced motion сохраняли приоритет.

Модели ноды/задачи находятся в `src/types.ts`. `src/api.ts` оставлен тонким фасадом для
совместимости старых импортов. Прикладные компоненты получают тот же `T` из `api<T>`;
добавление frontend framework не меняет серверный контракт. Сообщение и детали ошибки,
возвращённые backend, сохраняются; неизвестные серверные коды принимаются как строки.

## Проверки

Каталог покрыт проверками полноты, параметров и неизменяемости. Проверяется совпадение
серверных error codes с frontend. Архитектурный тест запрещает новые текстовые литералы
в собственных raise/emit/logger-вызовах вне каталога. Frontend-тесты проверяют API-клиент,
загрузку/доступность общих компонентов, форматирование и fallback статусов.

```bash
cd backend
poetry run pytest -q
cd ../frontend
npm test
npm run build
```
