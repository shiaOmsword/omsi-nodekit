# SSH-выход для установленной панели

Нода → **SSH-туннели**. Доступно для активной панели 3x-ui 3.11.0,
установленной Nodekit и имеющей manifest. Работа с панелью в системе и Docker
с host network одинакова. XHTTP на входе Москвы совместим с этим сценарием:
внешний транспорт телефона независим от межсерверного RAW/REALITY внутри SSH.

## Подготовка

1. На выходной VPS создать VLESS/RAW/REALITY inbound и клиента. Inbound должен
   принимать соединения на **127.0.0.1:8443** выходной VPS (порт можно выбрать другой).
2. В 3x-ui Москвы добавить обычный VLESS/RAW/REALITY outbound с параметрами этого
   клиента: UUID, flow, SNI, public key и short ID. Операция использует его как
   источник настроек и оставляет исходную запись неизменной. Автоматического
   импорта клиента из другой панели в этой версии нет.
3. На **московской VPS** подготовить SSH-ключ без интерактивной passphrase;
   добавить его публичную часть в authorized_keys пользователя выходной VPS.
   Пути identity_file/known_hosts_file ниже относятся к московской VPS,
   а не к компьютеру, где запущен Nodekit. Пользователь tunnels.user должен
   существовать на обеих VPS; на Москве от его имени запускается служба SSH.
4. Записать проверенный host key выходной VPS в known_hosts. Для нестандартного
   порта SSH запись должна соответствовать `[host]:port`. Private key обычно
   имеет права 600 и принадлежит пользователю службы. В SSHD выходной VPS
   разрешить local TCP forwarding к 127.0.0.1:8443. Для ключа с `restrict` отдельно
   разрешить `port-forwarding,permitopen="127.0.0.1:8443"`.
5. Добавить tunnels в существующий YAML Москвы, сохранив остальные параметры:

```yaml
tunnels:
  - name: gb
    host: 203.0.113.20  # заменить адресом выходной VPS
    user: omsi
    ssh_port: 2222     # фактический SSH-порт выходной VPS
    local_port: 15443
    target_port: 8443
    identity_file: /home/omsi/.ssh/gb_xray_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
```

У каждого туннеля должны быть уникальные name и local_port; имя panel
зарезервировано. Порт local_port публично в UFW открывать не требуется.
Если исходный inbound выхода доступен только внутри изолированной Docker-сети,
сначала обеспечить его доступность с loopback выходной VPS.

## Туннели → балансировщик → маршрут

Сохранить YAML и обновить обнаружение на вкладке **SSH-туннели**.

1. **Один туннель**: выбрать запись из YAML и образец VLESS/RAW/REALITY outbound.
   Nodekit запускает отдельную SSH-службу, создаёт копию outbound с loopback
   адресом и проверяет HTTPS. Inbound на этом шаге не выбирается, маршруты
   сохраняются. UUID, SNI, ключи и параметры исходного outbound не меняются.
2. **Создать балансировщик**: задать уникальный tag, отметить подготовленные
   выходы и выбрать fallback. Стратегия — `roundRobin`, fallback по умолчанию
   **`direct`**. При отказе всех участников трафик может выходить через саму
   VPS, например через Москву. Для блокировки выбрать существующий blackhole
   outbound, обычно `blocked`. Fallback должен существовать и не входить в
   список участников. Выбор сохраняется в Xray, а не в отдельном реестре.
3. **Настроить маршрут**: выбрать существующее простое правило или создание
   нового, отметить **все** нужные inbound (например, WG и VLESS), выбрать
   балансировщик и посмотреть план. Балансировщики, созданные вручную в
   3x-ui, тоже доступны. Новое правило добавляется в конец таблицы; изменение
   существующего сохраняет его позицию и служебные поля панели. Другие
   правила не удаляются и не переупорядочиваются.

Таблицы показывают сохранённые балансировщики, их фактических участников по
селекторам и правила. Отчёт о реально запущенном routing остаётся отдельно
на вкладке сети. Ввод и редактирование условных, выключенных и API-правил
выполняются в 3x-ui. Если inbound уже имеет полное правило, выбрать именно
его для редактирования: новая пересекающаяся запись отклоняется. Более ранние
условные правила продолжают действовать; более ранний безусловный catch-all
блокирует создание неработающего маршрута. При снятии отметки inbound
использует остальные правила, в том числе `direct`, если он настроен.

Селекторы Xray сопоставляются **по префиксу**: `ssh-node-de` захватывает и
`ssh-node-de2`. Nodekit проверяет полный состав при создании балансировщика
и отклоняет выбор, который молча включил бы неотмеченные выходы. Тогда выбрать
оба участника или заранее использовать разные, не пересекающиеся имена.
Существующие балансировщики показывают фактические совпадения.

Проверка доступности использует существующий `observatory`, добавляя только
селекторы; при наличии `burstObservatory` сохраняется он. Для нового observer
используется прежний профиль Nodekit (HTTPS generate_204, 15 секунд). Прочие
параметры observer сохраняются. Выключенный вручную туннель останется в
конфигурации балансировщика: исключение недоступного пути зависит от его
следующей пробы, а не происходит мгновенно.

Для WG на Москве европейский WG не нужен: Xray принимает WG-клиента и
направляет его трафик через VLESS/SSH-выход. Сам WG-порт UDP через SSH не
пробрасывается. HTTPS-проба выхода не проверяет подключение WG-клиента,
DNS/UDP/QUIC приложений или весь маршрут с телефона — проверь их отдельно.

Перед изменением проверяется fingerprint всего сохранённого Xray template,
а для маршрута — ещё и выбранных inbound. Сохраняются приватные SQLite/JSON
снимки. Применение идёт через API 3x-ui, затем проверяется сгенерированный
runtime. `enabled` и `comment` сохраняются в шаблоне; в runtime 3x-ui удаляет
их. Запись маршрута не требует новой HTTPS-пробы каждого туннеля: это отдельный
этап подготовки выходов, и остановленный участник может иметь рабочий fallback.

При ошибке выполняется откат только собственного изменения, если шаблон
по-прежнему совпадает с записанным. Параллельные изменения оператора не
перезаписываются. Снимки содержат секреты и остаются приватными на VPS.
Старые действия API `tunnel`/`tunnel_route` сохранены для уже настроенных
выходов; новый интерфейс использует `tunnel_setup`, `xray`, `tunnel_control`.
Если старое собственное правило переводится на другой балансировщик, его
metadata отвязывается от inbound; SSH-служба, ключи и outbound сохраняются.
Балансировщики и правила уже входят в SQLite-бэкап панели.

Источник формата и поведения селекторов:
[Xray routing](https://xtls.github.io/en/config/routing.html),
[observatory](https://xtls.github.io/en/config/observatory.html).

## Завершающая проверка и временный отказ HTTPS

В журнале различаются два этапа после применения routing:

- `runtime route verification` (для пула — `runtime pool route verification`):
  ожидание точного собственного outbound, routing rule и, для пула, balancer
  в сгенерированном runtime-конфиге. Совпадение только имени тега недостаточно.
- `HTTPS return traffic after routing update` (также для пула и общего выхода):
  отдельная HTTPS-проба через существующий SSH/VLESS-путь. Сбой этой пробы
  после успешной проверки runtime не означает ошибку SSH-ключа.

Для завершающей HTTPS-пробы по умолчанию выполняются максимум **3 попытки**.
При временном отказе в журнале видны номер попытки и безопасная причина:
например, `timeout`, `TCP connect`, HTTP-код или отсутствие тела ответа.
Между попытками используется существующий `readiness_interval`. Каждый запрос
ограничен `probe_timeout`; SSH-службы и routing повторно не создаются.
Постоянный отказ вызывает прежний scoped rollback. Проверка перед изменениями
остаётся отдельной: без первоначального HTTPS-ответа маршруты не применяются.

Число попыток задаётся в окружении **локального backend Nodekit**:
`NODEKIT_DEPLOYMENT__TUNNEL_PROBE_ATTEMPTS=3` (от 1 до 5; 1 отключает повторы).
Это не поле YAML ноды. Для длительности одного HTTPS-запроса используется
существующая настройка `NODEKIT_DEPLOYMENT__PROBE_TIMEOUT` (по умолчанию 20 секунд).

При таймауте runtime журнал отдельно показывает `config`, `outbound`, `route`
и `balancer`: доступен ли JSON, найден ли outbound и совпадают ли его поля,
есть ли правило и balancer. Полный JSON, UUID, ключи и тело HTTP-ответа не
выводятся. После успешной HTTPS-пробы шаблон повторно сверяется перед записью
ownership, чтобы длительное ожидание не затёрло параллельное изменение оператора.
Nodekit автоматически не перезапускает всю панель 3x-ui для обхода этой ошибки.

Операция:

- проверяет fingerprint inbound и принадлежность systemd-службы;
- сохраняет приватные SQLite и Xray template snapshots на VPS;
- включает loopback-only SSH-forward с StrictHostKeyChecking, IdentitiesOnly,
  BatchMode, ExitOnForwardFailure, keepalive и Restart=always;
- использует `-F none`, исключая скрытые LocalForward/ProxyCommand из SSH config;
- получает непустой HTTPS-ответ через настоящий выходной VLESS inbound;
- создаёт outbound `ssh-<node>-<tunnel>` с локальным SSH endpoint; UUID, SNI,
  ключи, short ID и flow сохраняются;
- добавляет маршрут только выбранного inbound после начальных API/blackhole
  правил, сохраняя исходный outbound, default outbound и остальные правила;
- сохраняет template через API, перезапускает Xray и сверяет runtime;
- при ошибке откатывает template и состояние службы. Если template параллельно
  изменил оператор, чужие изменения не затираются: выводится ошибка отката,
  рабочий forward сохраняется для текущего маршрута.

Повторное применение тех же параметров допустимо; при этом порядок имеющихся
outbound и правил сохраняется. Один туннель привязывается к одному inbound.
Смена inbound через существующую запись отклоняется, чтобы молча не снять
старый маршрут. Изменение порта того же inbound отслеживается по его ID и
обновлённому тегу 3x-ui. Manifest фиксирует только применённые туннели: если
в YAML добавлено несколько новых записей, применить каждую перед следующей
настройкой подписок. Чужая или изменённая systemd-служба не перезаписывается.
Службы прежнего формата без `-F none` требуют ручного согласования конфигурации.

## Проверка и восстановление

Доктор проверяет systemd и loopback listener туннелей из YAML. SSH-выход
дополнительно проверяет UUID/REALITY, передачу запроса и получение HTTPS-ответа.
Проверка не доказывает внешнюю доступность телефона и не проверяет геолокацию IP.
После применения открыть сайты и проверить внешний IP на телефоне:
ожидается IP выбранной выходной VPS.

Для возврата: в 3x-ui убрать правило с outboundTag `ssh-<node>-<tunnel>`
или направить выбранный inbound на direct. Затем можно остановить службу
`omsi-<node>-<tunnel>.service`. Предыдущий template и SQLite сохранены как
`before-tunnel-<timestamp>.json` и `.db` в каталоге ноды; эти файлы приватные.
Удаление записи ноды из локальной панели не удаляет удалённую SSH-службу.

SSH `-L` переносит TCP. Сырой UDP-порт он не открывает: UDP-приложения требуют
совместимого переноса UDP внутри VLESS и поддержки этого режима клиентом.

## Границы этой версии

Требуются подготовленные межсерверный SSH-ключ, known_hosts и исходный
outbound. Автоматическая выдача ключей/authorized_keys, импорт клиентов
между панелями, создание произвольных XHTTP outbound и кросс-провайдерный failover
в этот PR не входят. Guarded XHTTP ingress и SSH-пул описаны выше;
новый раздельный workflow требует отдельного live прогона. Безопасность RAW/REALITY относится к межсерверному
участку и не меняет проверенный XHTTP/TLS профиль телефона.

## Воспроизводимый локальный smoke

`backend/tests/runtime/ssh_exit_smoke.py` создаёт временные панели, ключи и
loopback listeners. Проверяет XHTTP/TLS → Caddy → московская 3x-ui → OpenSSH
клиент → выходной REALITY → HTTPS и получает полный ответ 188416 байт.
Проверяется и повторное применение. systemctl симулируется; настоящий
OpenSSH исполняет сгенерированный ExecStart. Публичная VPS не используется.

В одноразовой Linux root-среде с бинарниками 3x-ui, Xray, Caddy и sshd:

```bash
cd backend
PYTHONPATH=src poetry run python tests/runtime/ssh_exit_smoke.py \
  --panel /path/to/x-ui \
  --xray /path/to/bin/xray-linux-amd64 \
  --caddy /path/to/caddy \
  --sshd /usr/sbin/sshd
```

Для OpenSSH server backend нужен `/run/sshd`. Если контейнер запрещает
`setgroups`, можно отдельно установить **только в тестовую среду**
`paramiko==5.1.0` и вместо `--sshd` передать `--ssh-backend paramiko`.
Тогда сервером выступает настоящий SSH fixture на Paramiko, а проверка
читаемости файлов root через runuser заменяется os.access. SSH-клиент,
3x-ui, Xray, TLS и весь трафик остаются настоящими. В приложении Paramiko
не используется и не добавляется в production dependencies.


## Форматы VLESS и сообщения preflight

SSH-выход поддерживает плоские settings (`address`, `port`, `id`, `encryption`,
`flow`, `testseed`) и прежний `vnext` с одним endpoint и списком пользователей.
Исходный формат сохраняется; меняются только tag копии, адрес и порт назначения.
Смешивать обе схемы в одном outbound нельзя. UUID, REALITY, flow и testseed
сохраняются без изменений. В runtime smoke по умолчанию проверяется плоский
outbound; `--outbound-format vnext` повторяет проверку прежнего формата.

При отказе подготовки журнал показывает конкретную известную проверку:
формат outbound, актуальность inbound, принадлежность маршрута/службы,
доступность ключа/known_hosts или занятый порт. Неожиданные ошибки показывают
подэтап и класс исключения. Полные settings, ответы API, UUID и приватные ключи
в журнал не выводятся. Preflight выполняется до запуска новой службы, поэтому
пустой systemd journal при таком отказе возможен. После обновления Nodekit
обновить обнаружение и заново открыть модалку SSH-выхода.

## Пул независимых SSH-сессий (новый экспериментальный сценарий)

Вкладка **Нода → SSH-туннели** показывает записи `tunnels` из YAML и
read-only systemd status на VPS. Если настроен только один SSH-выход, кнопка
**«Подготовить 3 в YAML»** создаёт две копии с новыми именами и локальными
портами. Это изменяет только локальную конфигурацию Nodekit, а не VPS.
Сверить порты, сохранить настройки, обновить обнаружение, затем
**«Поднять пул»**.

Пример — три независимых процесса `ssh -N -T`, с одним и тем же exit VLESS:

```yaml
tunnels:
  - name: nd
    host: 203.0.113.20
    user: omsi
    ssh_port: 2222
    local_port: 15443
    target_port: 11474
    identity_file: /home/omsi/.ssh/exit_gb_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
  - name: nd-2
    host: 203.0.113.20
    user: omsi
    ssh_port: 2222
    local_port: 15444
    target_port: 11474
    identity_file: /home/omsi/.ssh/exit_gb_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
  - name: nd-3
    host: 203.0.113.20
    user: omsi
    ssh_port: 2222
    local_port: 15445
    target_port: 11474
    identity_file: /home/omsi/.ssh/exit_gb_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
```

В мастере **«Поднять пул»** отметить от 1 до 6 YAML туннелей, выбрать образец
для недостающих outbound, tag балансировщика и fallback (по умолчанию direct).
Совпадающие собственные SSH-службы и outbound, включая выходы старых пулов,
используются повторно. Недостающие ресурсы создаются, существующие маршруты
сохраняются. Если новый балансировщик уже существует и точно совпадает,
он используется повторно. При другом составе с тем же tag операция
останавливается; выбрать новый tag или изменить конфигурацию в 3x-ui.

Образец применяется только к новым выходам. Для разных выходных endpoint
сначала подготовить туннели по одному с соответствующими образцами, затем
собрать балансировщик. В пакетной операции проверяются все unit-файлы перед
первым запуском и каждый путь по HTTPS. Чужие/изменённые службы и outbound
не подменяются. Появление нового outbound, который был бы захвачен селектором
существующего балансировщика, отклоняется.

Три SSH-сессии до одного хоста не защищают от отказа самой выходной VPS.
Существующие TCP-соединения при отказе не переносятся на другую сессию.
Новые балансировщики используют выбранный fallback; старые пулы сохраняют
ранее выбранный `blocked`, пока оператор явно не изменит его.

После создания пула отдельно выполнить **«Настроить маршрут»**, затем
проверить выходной IP и WG/VLESS, DNS и UDP с клиентского устройства.

## Первый SSH host key: строгая проверка и опциональный TOFU

В примерах используется `198.51.100.20` из документального диапазона
TEST-NET-2; все IP, имена и ключи нужно заменить перед применением.

Подключение с рабочего ПК не заполняет
`/home/omsi/.ssh/known_hosts` на **московской VPS**.
Сервер `198.51.100.20` на портах `22` и `2222` обычно имеет
разные записи в `known_hosts`: для стандартного порта `198.51.100.20`,
для нестандартного `[198.51.100.20]:2222`.
Из-за `StrictHostKeyChecking=yes` и `BatchMode=yes` первый
неизвестный host key блокирует systemd SSH forward без приглашения.

По умолчанию Nodekit сохраняет строгую проверку. Чтобы один **новый**
SSH endpoint мог принять ключ сервера при первом соединении,
явно добавь в YAML конкретного туннеля:

```yaml
  - name: nd-3
    host: 198.51.100.20
    user: omsi
    ssh_port: 22
    local_port: 15445
    target_port: 11474
    identity_file: /home/omsi/.ssh/exit_gb_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
    host_key_policy: accept-new
```

Это включает `StrictHostKeyChecking=accept-new` и сохраняет `BatchMode=yes`
и `IdentitiesOnly=yes`. **Новый** host key сохраняется в `known_hosts`,
а если известный fingerprint **изменился**, OpenSSH разрывает соединение.
`StrictHostKeyChecking=no` не используется. В режиме TOFU пользователь
SSH-службы должен иметь право записи в свой `known_hosts` или его
родительский каталог (если файла пока нет). Символьные ссылки в TOFU
запрещены. По соображениям безопасности этот режим не включён по
умолчанию: на первом подключении возможна атака посредника; для
критичных нод лучше проверить fingerprint через независимый канал.

Проверить с московской VPS без изменения Nodekit:

```bash
ssh-keygen -F 198.51.100.20 -f /home/omsi/.ssh/known_hosts
ssh-keygen -F '[198.51.100.20]:2222' -f /home/omsi/.ssh/known_hosts

ssh -F none -p 22 -i /home/omsi/.ssh/exit_gb_tunnel \
  -o UserKnownHostsFile=/home/omsi/.ssh/known_hosts \
  -o StrictHostKeyChecking=yes \
  -o IdentitiesOnly=yes -o BatchMode=yes -v \
  omsi@198.51.100.20 true
```

Если неизвестный host key — будет `Host key verification failed`.
Если отклонён ключ пользователя — `Permission denied (publickey)`.
Если TCP forwarding запрещён на выходной VPS — проверить настройки
`AllowTcpForwarding`, `PermitOpen`, ограничения в `authorized_keys`
и `journalctl -u omsi-example-nd-3.service`.

Важное ограничение: на уже существующем systemd unit изменение
`host_key_policy` меняет `ExecStart`. Nodekit намеренно не
перезаписывает unit, если он отличается от сгенерированного. Для
применения новой политики к ранее созданной службе требуется
контролируемое обновление только доказанно принадлежащего Nodekit unit.

## Перезапуск установленных SSH-туннелей

**Нода → SSH-туннели → Перезапустить** в строке перезапускает только этот
туннель. **Перезапустить все** выбирает все `tunnels` текущего сохранённого YAML.
В плане перечисляются имена; кнопка **Перезапустить туннели** запускает задание.
Имена служб выводятся из service_prefix, node.id и tunnels.name: например,
`omsi-example-de.service`. Произвольное имя службы через API передать нельзя.

Нужна managed-конфигурация Nodekit и уже установленные службы. До первого
перезапуска проверяются все выбранные unit-файлы, FragmentPath, отсутствие
systemd drop-ins и pending daemon-reload, доступ пользователя к SSH-ключу и
known_hosts. Изменённый/чужой или отсутствующий unit останавливает операцию.
Проверка повторяется непосредственно перед перезапуском каждого участника.

Службы перезапускаются по очереди; после каждой проверяются active и локальный
TCP-listener. При ошибке следующая не перезапускается; предыдущие подключения
не откатываются. В журнале видны начало и результат для каждой службы, а отчёт
обнаружения обновляется и при неудаче. Процесс/listener не доказывают HTTPS-выход:
его следует проверить отдельной пробой трафика.

Операция вызывает только `systemctl restart` выбранных SSH-служб: unit-файлы,
enablement, маршруты, UUID/ключи, Xray и Caddy сохраняются. Трафик через эти
туннели кратковременно прерывается. После применения BBR/CUBIC здесь можно
переподключить SSH-сессии, чтобы новые исходящие TCP-сокеты использовали текущую
настройку ядра. Перезапуск не включает BBR и не гарантирует прирост скорости.

## Включение и выключение туннеля

Кнопки в строке туннеля открывают план, затем запускают `enable --now` или
`disable --now` только для проверенной установленной службы Nodekit. Это
меняет и состояние процесса, и автозапуск. Проверяются active, enabled и,
при включении, локальный listener. При ошибке восстанавливаются прежние
состояния уже затронутых служб, если их unit-файлы не изменились.

Выключение прерывает текущий трафик через этот туннель. Конфигурация Xray,
ключи и остальные туннели сохраняются; для новых соединений балансировщик
использует оставшихся участников или свой fallback после обновления health
проб. С `direct` внешний IP может стать адресом этой VPS.

## Локальная проверка этого обновления

Существующие backend/frontend проверки и сборки выполняются отдельно от
live проверки. Два прежних frontend сценария окна SSH обновлены под
подготовку без inbound; новые тестовые файлы не добавляются в этом этапе.
Новый workflow дополнительно проверяется локальными пробами с симуляцией
API/systemd: повторное применение, WG + VLESS, откат при сбое, устаревший
fingerprint и сохранение параллельного изменения. Это не заменяет проверку
реального SSH/Xray и клиента на VPS.
