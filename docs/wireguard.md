# WireGuard inbound и перенос ключей

Во вкладке **Inbound → + WireGuard** можно создать WG с первым клиентом либо
восстановить отдельный WG inbound из загруженного `.db` или `.nodekit.zip`. Используется текущая
managed 3x-ui 3.11.0 через её API; отдельный WG-сервер и новое хранилище ключей
не добавляются. Ключи генерирует уже используемый X25519 API панели.

## Сеть и Caddy

WG слушает публичный **IPv4 UDP** порт (по умолчанию 51820). Nodekit проверяет
занятость UDP и, при активном управляемом UFW, добавляет точное разрешение.
После создания и редактирования проверяется UDP listener; TCP-проба к WG не
выполняется. Отсутствие UDP listener после создания запускает scoped rollback.
При редактировании/удалении используются существующие транзакции UFW; занятые
UDP-порты других процессов сохраняются. UFW не включается и не сбрасывается.
Firewall/security group провайдера надо разрешить отдельно.

Перед созданием нужны включённые HTTPS-подписки этой панели через Caddy с
согласованным subURI. WG `wireguard://` выдаёт сама 3x-ui; Caddy продолжает
передавать HTTPS-запросы к её subscription backend существующим маршрутом.
Приватные ключи не добавляются в отчёты, журналы или отдельный публичный сайт.

**UDP-пакеты WireGuard идут напрямую на WG listener.** Обычный HTTP
`reverse_proxy` Caddy их не передаёт. Nodekit не меняет Caddy image и не включает
сторонний caddy-l4 автоматически. Порт 443/udp может уже использоваться Caddy
HTTP/3: такой listener нельзя перехватывать. Если нужен именно L4 UDP proxy,
это отдельный профиль развёртывания с проверкой модулей, публикаций и конфликтов.

## DNS и клиент

В форме задаётся DNS endpoint, например `wg.example.net`, с A-записью на VPS.
Он сохраняется в native shareAddr 3x-ui и входит в выдаваемые WG-профили.
Обнаружение сравнивает A-записи с адресом SSH назначения и показывает расхождения.
Результат с VPS не доказывает DNS или доступность UDP на телефоне.

В этой реализации listener IPv4. Не добавляй AAAA до отдельной настройки и
проверки IPv6 listener/firewall; иначе клиент может выбрать неработающий IPv6.
DNS в настройках клиентского профиля — отдельное поле с IP-адресами DNS-серверов,
оно не заменяет endpoint. MTU настраивается отдельно; значение по умолчанию
не считается результатом измерения конкретного маршрута.

## Управление и перенос

Чтобы московский WG использовал европейский VLESS/SSH-выход, подготовь
туннели, создай балансировщик и обнови обнаружение. Во вкладке **SSH-туннели →
Настроить маршрут** выбери существующее правило VLESS, отметь WG вместе
с VLESS и выбери общий балансировщик. Ручные балансировщики 3x-ui тоже
доступны. Дополнительный WG inbound на Европе и новая SSH-служба для
добавления WG не нужны. По умолчанию у нового балансировщика fallback
`direct`: при отказе всех туннелей выход может идти через Москву. Для
блокировки выбери blackhole.
См. [общие SSH-выходы](ssh-egress.md#туннели--балансировщик--маршрут).

- **Изменить**: имя, публичный порт, DNS endpoint, MTU и клиентский DNS.
  Серверный secretKey и все peer identities сохраняются.
- **+ / − Клиент**: используются Clients API и SQLite snapshot. Новому клиенту
  выделяется свободный IPv4 /32, ключевая пара и subId. Удаление аккаунта,
  привязанного также к другому inbound, отклоняется вместо глобального удаления.
- **Подписки и ключи**: WG-клиенты доступны для проверки DNS/HTTPS выдачи;
  ключи остаются в панели. Проба VLESS/REALITY не выдаётся за WG handshake.
- **Восстановить WG из SQLite** переносит server secretKey, peer private/public
  key (если private был сохранён), PSK, allowedIPs, keepalive, существующие subId
  и политики клиента. Нормализованные clients/client_inbounds задают принадлежность аккаунта и
  его политики. WG peer keys/allowedIPs берутся из settings конкретного inbound:
  у одного аккаунта на WG/AWG могут быть разные ключи и адреса. Если peer отсутствует,
  global WG fields допустимы только при единственной tunnel-привязке.
  Старые embedded clients/peers без нормализованной схемы тоже поддерживаются.
  Противоречивая/неполная схема отклоняется, а не заменяется новыми ключами.
- Существующие конфликтующие email/subId/ключи не объединяются автоматически.
  После ошибки сначала обновить обнаружение: повтор с тем же именем/портом
  не создаёт второй inbound. Снимок остаётся на VPS для явного восстановления.

Для прежних клиентских конфигов нужны **тот же server key, peer key/PSK,
адреса, endpoint domain и UDP port**. На новой VPS меняется A-запись домена.
Один DNS update не гарантирует немедленное переподключение уже работающего WG:
некоторые клиенты разрешают endpoint только при запуске. Нужны reconnect или
клиентский механизм повторного DNS resolve. Клиентский private key нельзя
восстановить из public key; peer без сохранённого private продолжит принимать
старое устройство, но повторно выдать его конфиг с сервера нельзя.

## Граница этого этапа

Работа опирается на upstream tag v3.11.0 (c621ba9), а не на изменчивый main.
Существующие CI/сборка и изолированная проверка каталога/плана выполняются сейчас;
новые тестовые файлы по просьбе пользователя оставлены отдельному этапу.
Live WG handshake/маршрутизация и реальная 3x-ui API интеграция ещё не проверены.
После review: создать тестового клиента, получить профиль через HTTPS Caddy,
проверить handshake и трафик с внешнего устройства, затем перенос в отдельную
тестовую панель с прежними ключами и сменой только DNS.

Выборочное WG восстановление принимает `.db` и `.nodekit.zip`: каталог и
задание используют общий helper проверки архива и извлечения `x-ui.db`.
WG-ключи входят в SQLite-снимок системного бэкапа. Выборочный перенос WG не
применяет TCP-настройки и SSH-ключи из ZIP; для них есть отдельная операция
системного восстановления. Перезапуск SSH-туннелей и сетевые замеры остаются
отдельными действиями во вкладках ноды.

План переноса с wg-easy, различия ключей/Endpoint/подписки и ограничения DNS:
[миграция WireGuard](wireguard-migration.md).
