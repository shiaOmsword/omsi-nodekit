# Существующие ноды, SSH-ключи и встроенная справка

В боковом меню панели теперь есть **«Ноды»**, **«SSH-ключи»** и **«Справка»**. Начни с
«Справка → Первое подключение». Там же доступны инструкции для системной 3x-ui,
Docker, TLS/Caddy, восстановления и разбора ошибок.

## Выбрать сценарий

| `panel.installation` | Что выбирается | Доступные операции |
| --- | --- | --- |
| `managed` | Native или Docker-панель этой ноды, созданная Nodekit | Обнаружение, диагностика, бэкапы и поддерживаемое управление; fresh/restore только на пустую цель |
| `auto` | Единственная обнаруженная панель | check, doctor, backup |
| `native` | Системная 3x-ui, по умолчанию `x-ui.service` | check, doctor, backup |
| `docker` | Существующий контейнер; можно задать `panel.container` | check, doctor, backup |

Старые YAML без `installation` сохраняют режим `managed`. Для подключения к уже
работающей ноде выбери `auto`, `native` или `docker`. При нескольких подходящих панелях
`auto` выдаст отчёт, но **не выберет панель за тебя**. Для doctor/backup укажи тип и,
при необходимости, имя контейнера. Параметры портов/путей из YAML относятся к новой
управляемой установке: для существующей диагностика использует настройки из SQLite.

На VPS нужен Python **3.11+** со стандартным `sqlite3`, root либо `ssh.sudo: true`
с настроенным повышением прав: без пароля (`sudo -n`) или с `sudo_password`/`sudo_password_env`. Для чтения системной установки Docker не требуется.
Для новой Docker-панели нужны Docker/Compose; для native-панели и SSH-служб —
systemd/OpenSSH. Native без Docker Caddy не требует Docker. В этой версии
агент работает на Linux; локальную панель и тесты можно запускать на Windows/Linux.

## Системная установка

```yaml
id: existing-native
name: Существующая системная панель
ssh:
  host: 203.0.113.10
  user: root
  port: 22
  identity_file: ~/.ssh/id_ed25519
  known_hosts_file: ~/.ssh/known_hosts
panel:
  installation: native
  service: x-ui
  # Необязательно: путь переопределяет обнаруженный XUI_DB_FOLDER.
  # database_path: /etc/x-ui/x-ui.db
caddy:
  enabled: false
tunnels: []
probe: null
```

`203.0.113.10` — пример. Сохрани свой YAML, запусти **«Обнаружить установку»**, затем
**«Диагностика»**. Отчёт сохраняется вместе с задачей и виден под журналом.

Nodekit читает systemd-метаданные и эффективный `XUI_DB_FOLDER` из окружения процесса.
Для остановленного сервиса используются известные env-файлы (`/etc/default/x-ui`,
`/etc/conf.d/x-ui`, `/etc/sysconfig/x-ui`) и Environment из systemd; shell-код не исполняется.
Нестандартные env-файлы/drop-ins у остановленного сервиса могут потребовать явного
`database_path`. Системы без systemd не дают полной информации о состоянии процесса.

Из SQLite возвращаются web/sub listener, порт, путь, домен, включённость
подписок, пути TLS-файлов и ограниченный инвентарь inbound/клиентов без секретных ID. Пароли пользователей, API/Telegram-токены, session secret
и Xray/REALITY-конфигурация в отчёт не попадают. Полный `.db` в бэкапе содержит секреты,
поэтому хранится отдельно в локальном каталоге данных.
Отсутствующие строки settings дополняются стандартными значениями 3x-ui и перечисляются
в `defaulted_settings` отчёта. Для нестандартных версий значения можно переопределить
через `NODEKIT_DISCOVERY__PANEL_DEFAULTS` (JSON-словарь); такой fallback нужно сверить
с фактической версией панели до вывода о доступности listener.

## Существующий Docker

В предыдущем полном YAML замени секцию `panel`:

```yaml
panel:
  installation: docker
  container: my-3x-ui
  # Путь ВНУТРИ контейнера, не на VPS-хосте.
  database_path: /etc/x-ui/x-ui.db
```

Nodekit находит контейнеры по образу 3x-ui; `container` позволяет выбрать конкретный
контейнер, в том числе с переименованным образом. Для Nodekit-managed контейнеров
используются Compose labels, связанные с `node.id`.
Путь к БД сопоставляется с bind/volume mounts, а при отсутствии mount — с файловой
системой работающего контейнера через `/proc/<pid>/root`. В недоступной файловой
системе или PostgreSQL снимок не создаётся; пустого бэкапа не будет.

Отчёт показывает image, network mode, имена сетей и опубликованные порты. Для doctor
используются host network или опубликованный TCP-порт. Если listener доступен только
из другой Docker-сети, отчёт это поможет разобрать, но Nodekit не подключает к ней
контейнеры автоматически. `127.0.0.1` внутри bridge-контейнера относится к нему самому.

## Встроенный TLS и существующий Caddy

`caddy.enabled: false` означает «не создавать новый Caddy». Обнаружение существующего
Caddy при этом работает. Если 3x-ui сама завершает TLS, отдельный reverse proxy не обязателен.

Отчёт проверяет `webCertFile`/`webKeyFile` и `subCertFile`/`subKeyFile`: наличие файлов,
доступность ключа агенту, даты и SHA256 fingerprint сертификата через `openssl x509`.
Приватный ключ не читается и не копируется. «Срок в порядке» не подтверждает цепочку
доверия, соответствие ключа сертификату или права самого процесса панели. Doctor
отдельно проверяет TLS handshake, доверенный CA и hostname из `webDomain`/`subDomain`,
подключаясь к обнаруженному listener. Проверка TLS не отключается; self-signed сертификат
потребует настроенного доверия на VPS. При отсутствии domain проверяется IP listener.
Для чтения метаданных нужен установленный `openssl`.

Системный Caddy ищется как `caddy.service`, контейнерный — по образу/имени/команде Caddy.
Путь извлекается из `--config` или задаётся явно:

```yaml
caddy:
  enabled: false
  service: caddy          # можно переопределить имя systemd unit
  config_path: /etc/caddy/Caddyfile
```

Для контейнера `config_path` относится к пути внутри контейнера. JSON читается напрямую,
Caddyfile адаптируется командой `caddy adapt` (в контейнере — `docker exec … caddy adapt`).
`--validate`, reload и restart при обнаружении не вызываются. Это позволяет разобрать
imports и вернуть сводку `listen → host/path → upstream`, не возвращая весь конфиг с
headers/auth/DNS-токенами. Новые сети, listeners и сертификаты не создаются.

Сводка относится **к файлу**, активная конфигурация после API-изменений может отличаться.
API-only, resume/autosave, caddy-docker-proxy, относительные пути, env-подстановки вне
контейнера и нестандартные модули требуют ручной проверки. Для поддерживаемой managed-панели уже есть отдельные планы подключения
[общего Caddy](subscriptions.md#подключение-caddy-после-установки-панели) и
изменения собственного сайта. Они требуют сверки файла с активной
конфигурацией и не присваивают произвольные чужие маршруты.
Если fresh/restore запрошен с новым Caddy, а на сервере обнаружен существующий Caddy,
операция остановится до развёртывания второго прокси.

## Создать ключ локально и запомнить его у ноды

1. В терминале, откуда запускается backend, проверь `ssh -V` и `ssh-keygen -?`.
   В Windows установи компонент «Клиент OpenSSH» либо используй WSL для всего backend.
2. Открой **«SSH-ключи»**, введи название и создай Ed25519. Публичная строка и fingerprint
   появятся в карточке. Приватного ключа в HTTP-ответах нет.
3. Через существующий доверенный SSH-доступ/консоль провайдера добавь публичную строку
   под пользователем, которого будешь указывать в `ssh.user`:

```bash
# На VPS под нужным пользователем; замени строку на настоящий публичный ключ.
install -d -m 700 ~/.ssh
printf '%s\n' 'ВСТАВЬ_ПОЛНУЮ_СТРОКУ_ssh-ed25519' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

4. На компьютере выполни `ssh -p PORT USER@HOST`, сверь fingerprint с консолью провайдера
   и только затем подтверди host key. Для порта 2222 нужна запись `[HOST]:2222`.
   Сгенерированный клиентский ключ и host key сервера — разные ключи.
5. Вернись к ноде, выбери ключ в форме и сохрани YAML. В нём появится `ssh.key_id`.
   При выбранном key_id используется управляемый файл; `identity_file` остаётся запасным
   вариантом после снятия выбора. `known_hosts_file` нужен в обоих случаях.
6. Запусти «Обнаружить установку». При необходимости проверь ключ вручную:

```bash
# На компьютере; подставь ID из сохранённого YAML.
ssh -p 22 -i backend/data/ssh-keys/<key_id>/id_ed25519 \
  -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes root@203.0.113.10 true
```

В native Windows используй `C:/Users/имя/.ssh/known_hosts` и путь к каталогу проекта,
где работает backend; пути с пробелами в ручной SSH-команде заключай в кавычки.
Если backend запущен в WSL, указывай Linux-пути. Значения `~` backend раскрывает для
своего пользователя ОС.

Пары лежат в `backend/data/ssh-keys/<id>/id_ed25519{,.pub}`. Каталог данных переопределяется
через `NODEKIT_DATA_DIR`, имя подкаталога — `NODEKIT_KEYS_DIRECTORY`, бинарник генератора —
`NODEKIT_SSH__KEYGEN_BINARY`. Используются права 700/600 в Unix; в Windows ACL ограничивается
SID текущего пользователя через `icacls`. При невозможности ограничить доступ генерация
завершается ошибкой. Название ключа хранится в SQLite; в имени файла используется UUID.

Ключ генерируется без passphrase для фонового `BatchMode`-подключения. Для ключа с passphrase
можно продолжать использовать внешний `identity_file` и предварительно разблокированный
`ssh-agent`. Сохраняй резервную копию каталога данных. Удаление из панели блокируется, пока
ключ привязан к сохранённой ноде или выполняется задача. Удаление локальной пары не удаляет
публичную строку с VPS — для отзыва доступа удали её из `authorized_keys` самостоятельно.
Ключи туннелей RU → outbound остаются отдельными файлами на RU; эта вкладка управляет
подключением **компьютер → VPS**.

## API и хранение

Обычные ответы сохраняют контракт `{ok,data,error,meta}` и локальную защиту запросов.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/ssh-keys` | Список публичных данных |
| `POST /api/ssh-keys` с `{"name":"…"}` | Создать локальную пару |
| `DELETE /api/ssh-keys/{id}` | Удалить непривязанную пару |
| `POST /api/config/ssh-key` с `{"yaml":"…","key_id":"…"}` | Изменить черновик; `null` снимает привязку |
| `POST /api/config/installation` с `{"yaml":"…","installation":"native"}` | Изменить тип установки в черновике |
| `GET /api/jobs/{id}` | Журнал и структурированный `report` либо `null` |

Форма пересобирает YAML без комментариев; изменения сохраняются только обычной кнопкой
«Сохранить». Миграция SQLite v2 добавляет `ssh_keys` и `job_reports`, сохраняя ноды, задачи
и бэкапы. Пути/ограничения обнаружения задаются через `NODEKIT_DISCOVERY__…` из Settings.

## Что проверено

Автотесты покрывают неизменность SQLite при обнаружении, whitelist секретов, выбор
установки, Caddyfile/JSON/network metadata, TLS verification, реальную генерацию Ed25519,
привязку/удаление и сохранение отчёта. Linux-only `pwd` и `fcntl` импортируются только
при исполнении соответствующих операций на VPS: импорт bundle и тесты локальной панели
работают без этих модулей. CI запускает backend/frontend на Ubuntu и Windows.

Автотесты не подтверждают SSH-доступ, выпуск сертификата и конфигурацию Caddy
конкретной VPS. Первый удалённый прогон — **check → doctor → backup**
на существующей ноде; полный fresh/restore выполняй на отдельных тестовых VPS по [FAQ](faq.md).

Форматы сверены с [настройками 3x-ui](https://github.com/MHSanaei/3x-ui/blob/main/internal/web/service/setting.go),
[systemd unit 3x-ui](https://github.com/MHSanaei/3x-ui/blob/main/x-ui.service.debian)
и [документацией caddy adapt](https://caddyserver.com/docs/command-line#caddy-adapt).


## Sudo с паролем

Подключение по SSH остаётся по ключу. Пароль ниже нужен для повышения прав через sudo,
он не заменяет SSH-ключ и не меняет sudoers. Пользователь должен иметь право выполнять
Python-агент от root. Наличие пользователя в группе sudo не означает NOPASSWD.

Для пользователя `omsi`, у которого sudo запрашивает пароль, добавь к своей секции `ssh`:

```yaml
ssh:
  host: 203.0.113.10
  user: omsi
  port: 22
  identity_file: ~/.ssh/id_ed25519
  known_hosts_file: ~/.ssh/known_hosts
  sudo: true
  sudo_password: 'ВАШ_ПАРОЛЬ_SUDO'
```

Пароль с символами `#`, `:`, `$` и пробелами заключай в YAML-кавычки. В одинарных
кавычках апостроф записывается дважды: `sudo_password: 'pa''ss'`. Пустые пароли,
переносы строки и NUL не принимаются. После изменения сохрани YAML и повтори check.

Вариант без значения пароля в YAML:

```yaml
ssh:
  host: 203.0.113.10
  user: omsi
  port: 22
  identity_file: ~/.ssh/id_ed25519
  known_hosts_file: ~/.ssh/known_hosts
  sudo: true
  sudo_password_env: OMSI_SUDO_PASSWORD
```

Задай `OMSI_SUDO_PASSWORD` в окружении процесса **локального backend** перед его запуском.
В PowerShell можно ввести значение без отображения:

```powershell
$secret = Read-Host 'Пароль sudo' -AsSecureString
$env:OMSI_SUDO_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
poetry run nodekit
```

В Bash:

```bash
read -rsp 'Пароль sudo: ' OMSI_SUDO_PASSWORD
export OMSI_SUDO_PASSWORD
poetry run nodekit
```

Ссылка не означает подстановку `${...}` внутри YAML. Не указывай оба источника сразу.
Пользовательская переменная читается из окружения запущенного backend, а не из браузера,
VPS или dotenv-файлов Settings. При смене окружения перезапусти backend.
Если `sudo_password`/`sudo_password_env` отсутствуют, остаётся прежний `sudo -n`.

Введённый прямо в YAML пароль сохраняется с конфигурацией в локальной SQLite и доступен
в YAML-редакторе; он не шифруется. Параметры sudo-аутентификации исключаются из bundle,
локального манифеста бэкапа и remote manifest. Типизированные модели скрывают значение
в repr/JSON, ошибки валидации не возвращают исходный пароль. Пароль передаётся только
через stdin зашифрованного SSH-соединения, не через argv или shell-интерполяцию.
Права sudoers/requiretty и многофакторная аутентификация автоматически не обходятся.

Передача учитывает sudo, которое читает пароль, и sudo с готовым timestamp/NOPASSWD,
которое пароль не читает: фрейм агента отделён маркером и не исполняет лишнюю строку.
Это также не требует очистки sudo-кэша и не меняет политику сервера.
