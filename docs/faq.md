# FAQ: первый прогон Nodekit

Начни с операции **«Проверить окружение»** на своей ноде. Она проверяет SSH, права,
Docker/Compose и systemd, не устанавливая панель и не меняя её настройки. Для полного
цикла `fresh → backup → restore` используй отдельную тестовую VPS; для restore — вторую
пустую VPS. Так результат можно проверить, пока рабочая нода продолжает обслуживать клиентов.

Все команды ниже — для Bash в Linux/WSL. Адреса `203.0.113.10` и `203.0.113.20` — примеры,
их обязательно заменить. Nodekit не создаёт VPS, SSH-пользователя, ключи или правила firewall.

## 1. Запустить локальное приложение

В своём клоне репозитория:

```bash
git fetch origin
git switch feat/local-control-panel
git pull --ff-only
cd frontend
npm ci
npm test
npm run build
cd ../backend
poetry install --with dev
poetry run pytest -q
poetry run nodekit
```

Открой **http://127.0.0.1:8765**. FastAPI раздаёт уже собранный React; отдельный Vite-процесс
для этого прогона не нужен. При изменении frontend нужно снова выполнить `npm run build`.
При использовании другого порта backend смотри `NODEKIT_SERVER__PORT` в env-примере.

На локальном компьютере нужны Python 3.12+, Poetry, Node.js 22.12+ либо 24 LTS и OpenSSH.
На VPS — Python **3.11+** (на Ubuntu 24.04 обычно 3.12), Docker Engine, Compose plugin и systemd.
Python-пакеты Nodekit на VPS устанавливать не нужно: агент и каталог сообщений передаются
по SSH в одном временном bundle. Если Python слишком старый, задача завершится понятной ошибкой.

## 2. Проверить SSH отдельно от приложения

Выбери уже существующий ключ, которым можешь входить на нужную VPS. Например, на компьютере:

```bash
ssh -p 2222 -i ~/.ssh/nodekit_test -o IdentitiesOnly=yes root@203.0.113.10
```

Если SSH работает на 22, замени `2222` на `22`. Сначала проверь fingerprint сервера,
затем прими его ключ: появится запись в локальном `~/.ssh/known_hosts`. Для нестандартного
порта она имеет вид `[адрес]:2222`. Fingerprint можно сверить в консоли провайдера:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Далее **в открытой SSH-сессии на VPS**:

```bash
python3 --version
docker info --format '{{.ServerVersion}}'
docker compose version
systemctl --version
```

Для non-root пользователя нужно неинтерактивное sudo. Проверь:

```bash
sudo -n true
```

Если оно недоступно, сначала реши вопрос прав либо используй подготовленный root-доступ.
Nodekit не запрашивает sudo-пароль в браузере. Если SSH-ключ зашифрован, предварительно
загрузи его в работающий `ssh-agent`: `ssh-add ~/.ssh/nodekit_test`.

Выйди из SSH-сессии и проверь **на компьютере** тот же вход без диалога:

```bash
ssh -p 2222 -i ~/.ssh/nodekit_test -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes root@203.0.113.10 true
```

Команда должна завершиться без запроса пароля/подтверждения host key. Только после этого
есть смысл проверять подключение из панели.

## 3. Добавить минимальную ноду

В панели нажми **«Добавить ноду»** и вставь полный конфиг ниже. Замени IP и пути на свои.
Пути в `ssh` относятся к компьютеру, на котором запущен backend Nodekit, а не к VPS.

```yaml
id: smoke-node
name: Тестовая VPS
ssh:
  host: 203.0.113.10
  user: root
  port: 2222
  identity_file: /home/omsi/.ssh/nodekit_test
  known_hosts_file: /home/omsi/.ssh/known_hosts
  sudo: false
panel:
  image: ghcr.io/mhsanaei/3x-ui:3.11.0
  port: 2053
  base_path: /nodekit/
  subscription_port: 2097
  subscription_path: /sub/
caddy:
  enabled: false
tunnels: []
probe: null
```

Для non-root пользователя укажи его имя и `sudo: true`. Нажми **«Сохранить»**.
Ожидаемый результат — уведомление о проверке и сохранении конфигурации.

Для проверки окружения существующей рабочей ноды остальные поля могут оставаться такими:
операция `check` их не применяет. Для её диагностики `doctor` уже нужны реальные порты,
путь HTTP панели и параметры туннелей.

## 4. Сделать первый запуск из панели

Выбери **«Проверить окружение» → «Показать план» → «Запустить»**.

В журнале появятся адрес SSH-подключения, сообщение о доступности Docker/Compose/OpenSSH/systemd
и `SSH/environment check complete; no services changed`. Статус задачи станет «Готово».
Если он «Ошибка», разбирать причину нужно до перехода к установке.

| Сообщение/симптом | Что проверить |
| --- | --- |
| `Local SSH file does not exist` | Путь к ключу/known_hosts на компьютере с backend |
| `Permission denied (publickey)` | Пользователя, ключ и его наличие в ssh-agent/authorized_keys |
| `Host key verification failed` | Предварительный вход, fingerprint, запись именно для нужного порта |
| Ошибка `sudo` или `Use root…` | `ssh.sudo` и выполнение `sudo -n true` |
| `Missing prerequisite` | Нужную программу на VPS; Nodekit не устанавливает её автоматически |
| Ошибка Docker daemon | `docker info` с теми же правами, что использует Nodekit |
| `Remote agent requires Python 3.11…` | Версию команды `python3` на VPS |
| Таймаут SSH | Сначала тот же ручной вход с тем же портом и ключом |

Для пользователя с ограниченными правилами forwarding/forced command обычного доступа
к туннелю может быть недостаточно: управляющему подключению нужно выполнять Python-команды.

## 5. Развернуть пустую панель на тестовой VPS

Используй этот шаг на **новой VPS**, где нет рабочей x-ui и существующего Compose-проекта
с таким же именем. Каталог `/opt/omsi-nodekit/smoke-node` должен отсутствовать либо быть пустым.
Порты `2053` и `2097` должны быть свободны. В первом прогоне оставь Caddy выключенным,
`tunnels: []` и `probe: null`: это позволяет проверить базовый цикл отдельно от межсерверной сети.

Выбери **«Развернуть с нуля» → «Показать план»**. Посмотри создаваемый `compose.yaml`,
затем запусти задачу. Образы могут загружаться несколько минут.

Ожидается: preflight, загрузка образа, создание учётной записи, запуск панели и проверка
HTTP. В журнале будет предупреждение, что проверка proxy-трафика не настроена. Это
ожидаемо: **fresh создаёт пустую панель**, без inbound, клиентов и outbound-профилей.

Проверка на VPS:

```bash
sudo docker compose -f /opt/omsi-nodekit/smoke-node/compose.yaml ps
sudo ss -lntp
sudo cat /opt/omsi-nodekit/smoke-node/credentials.json
```

Панель должна слушать `127.0.0.1:2053`, backend подписок — `127.0.0.1:2097`.
В credentials находятся логин и случайный пароль; в журнал задач пароль не выводится.

### Как открыть 3x-ui на компьютере

В отдельном локальном терминале оставь работающий SSH forwarding:

```bash
ssh -p 2222 -i ~/.ssh/nodekit_test -o IdentitiesOnly=yes -N -L 127.0.0.1:12053:127.0.0.1:2053 root@203.0.113.10
```

Открой **http://127.0.0.1:12053/nodekit/** и войди с данными из credentials.
При restore URL-путь и учётные данные берутся из бэкапа. Первый критерий успеха —
панель действительно открывается и принимает логин, а не только зелёный статус контейнера.

## 6. Проверить doctor и скачать бэкап

На той же ноде запусти **«Диагностика»**. Ожидается `Panel HTTP: OK`, проверка backend
подписок и явное `End-to-end proxy probe: NOT CONFIGURED`.

Затем выбери **«Скачать бэкап»** и дождись завершения. Скачай `.db` из журнала/блока бэкапов.
Снимок создаётся SQLite backup API, поэтому включает уже зафиксированные изменения из WAL.
В манифесте рядом со снимком сохранится конфигурация ноды.

Это бэкап управляемой Nodekit-панели в её каталоге, а не поиск произвольной существующей
БД на сервере. Внешние TLS-файлы, SSH-ключи и конфигурация ОС в `.db` не входят.
Бэкапы содержат чувствительные настройки, поэтому держи их вне Git.

## 7. Проверить restore на второй пустой VPS

Добавь ещё одну ноду с `id: smoke-restore`, другим IP и её локальным SSH-ключом. Остальные
поля возьми из первого конфига, включая **ту же версию image**, `base_path` и `subscription_path`.
Сначала выполни для неё `check`.

В операции **«Восстановить из БД»** загрузи скачанный `.db`, выбери его, посмотри план и запусти.
После завершения открой панель через SSH forwarding уже на вторую VPS.

Ожидается: сохранённые логин/пароль, настройки панели и, если они были в БД, клиенты,
UUID, subscription ID, REALITY-ключи и Xray template. Из свежего пустого бэкапа восстановится
пустая панель — это правильный результат. `credentials.json` при restore не создаётся:
используются учётные данные из БД.

Если файл отсутствует/повреждён, восстановление завершится ошибкой; переключения на fresh нет.
Первый тест с бэкапом рабочей ноды проводи только после этого цикла: проверь её версию,
пути к внешним файлам, bind на прежний IP и доступность нужных outbound.

## 8. Следующий этап: туннели, Caddy и реальный трафик

Параметры `tunnels` готовятся до установки ноды. Например, блок вместо `tunnels: []`:

```yaml
tunnels:
  - name: gb-22
    host: 203.0.113.20
    user: omsi
    ssh_port: 22
    local_port: 15443
    target_port: 443
    identity_file: /home/omsi/.ssh/gb_xray_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
  - name: gb-2222
    host: 203.0.113.20
    user: omsi
    ssh_port: 2222
    local_port: 15444
    target_port: 443
    identity_file: /home/omsi/.ssh/gb_xray_tunnel
    known_hosts_file: /home/omsi/.ssh/known_hosts
```

Здесь ключ и `known_hosts` уже должны существовать **на RU VPS** и читаться пользователем
`omsi`. На зарубежной VPS должны работать заданные SSH-порты и быть разрешён local forwarding.
Каждая запись создаёт отдельный SSH/systemd-процесс. Правила Xray outbound должны направлять
соединения на соответствующий `127.0.0.1:15443/15444`; Nodekit пока не создаёт их через API.

Для Caddy заранее подготовь DNS, свободный доступный порт 80 и HTTPS-порт подписок
(по умолчанию 2096). Включай его в конфиге **до fresh/restore новой ноды**.
Изменение сохранённого YAML само по себе работающую VPS не перенастраивает: повторный
`apply` ещё не реализован, а fresh/restore не перезаписывают заполненный каталог.

Если на VPS уже настроен локальный SOCKS inbound, направленный через нужный outbound,
его можно проверить без переустановки операцией doctor:

```yaml
probe:
  socks_port: 10808
  url: https://www.cloudflare.com/cdn-cgi/trace
```

Сохрани конфиг и запусти doctor. Жди реального успешного HTTPS-запроса через SOCKS.
Затем проверь подписку, загрузку сайтов и выходной IP **с пользовательского устройства**.
Живой SSH-процесс или открытый порт сами по себе не доказывают работу VPN.

## 9. Если развёртывание упало

Посмотри журнал задачи. При ошибке Nodekit пытается остановить только созданные им сервисы,
а файлы сохраняет для диагностики. Повторный fresh в этот каталог будет заблокирован.

Примеры команд на VPS:

```bash
sudo docker compose -f /opt/omsi-nodekit/smoke-node/compose.yaml ps
sudo journalctl -u omsi-smoke-node-gb-2222.service -n 50 --no-pager
```

Остановить именно этот тестовый Compose-проект, сохранив данные:

```bash
sudo docker compose -f /opt/omsi-nodekit/smoke-node/compose.yaml stop
```

Если добавлены SSH units, их остановка выполняется отдельно; например:

```bash
sudo systemctl stop omsi-smoke-node-gb-22.service omsi-smoke-node-gb-2222.service
```

После обрыва SSH, таймаута или перезапуска backend сначала проверь VPS: удалённая команда
может ещё выполняться. Автоматической очистки/удаления каталогов, отмены и rollback пока нет.
Не удаляй каталог с единственным экземпляром нужной БД ради повторного запуска.

## Что пока делается в самой 3x-ui

Создание и активация inbound/outbound, balancer, resolver, выдача клиентских профилей и
генерация REALITY-ключей через API Nodekit — следующие задачи. Сейчас они либо уже находятся
в восстановленном `.db`, либо настраиваются в 3x-ui. Переключение DNS и failover тоже остаются
отдельными действиями.

Архитектура и системные каталоги: [architecture.md](architecture.md), [messages.md](messages.md).
