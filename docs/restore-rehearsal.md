# Безопасная репетиция бэкапа и восстановления 3x-ui

**Статус:** инструкция и read-only аудит реализованы. Автоматическое удаление работающей
панели и полный production restore **не реализованы**. Не удаляйте 3x-ui на рабочей
московской VPS для эксперимента без отдельной проверенной процедуры.

## Граница управления

На `ultra` Nodekit управляет своей панелью 3x-ui и её ресурсами под
`/opt/omsi-nodekit/ultra`. Общий Docker daemon, контейнер `shared-caddy`,
проект `/opt/infra/caddy`, сеть `shared-proxy` и чужие сайты не принадлежат
панели и **никогда не должны удаляться, сбрасываться или заменяться целиком**.
В частности, запрещены `docker system prune`, `docker volume prune`,
`docker network prune`, `docker compose down` для проекта shared Caddy,
`ufw reset` и удаление общей сети.

Обозначения из 1 ноября 2026 года относятся к текущему примеру `ultra`;
перед любой операцией обнаружение должно подтвердить фактическую конфигурацию.

## Что сохраняется в .db, а что — нет

Nodekit использует согласованный SQLite backup API; перед отправкой проверяет
целостность и схему. В базе 3x-ui содержатся inbound/clients, настройки панели
и Xray template, включая сохранённые routing/outbounds. Внешние файлы не входят:

| Компонент | В SQLite .db |
| --- | --- |
| 3x-ui настройки, UUID и клиенты | Да, если хранятся в SQLite |
| Xray конфигурация, хранящаяся в 3x-ui DB | Да, по фактической схеме версии |
| systemd SSH units и их enable/active state | Нет |
| Отдельные SSH private keys и known_hosts на Москве | Нет |
| Caddyfile общего контейнера и TLS storage | Нет |
| Nodekit manifest / ownership / xhttp-routes / pool metadata | Нет |
| UFW allow правила | Нет |
| Compose file и контейнерный image reference | Нет |
| Состояние Docker volumes других проектов | Нет |

При restore на пустую VPS Nodekit может корректировать web/subscription
listeners и публичный URI по параметрам новой ноды. Поэтому byte-level
сравнение с исходной базой после настройки не обязательно совпадёт.

## Read-only проверка существующего backup

Скопировать backup в приватный каталог пользователя и указать оба SQLite файла,
например (команды только читают файлы и ничего не перезапускают):

```bash
python3 tools/backup_audit.py \
  --live /opt/omsi-nodekit/ultra/db/x-ui.db \
  --backup /home/omsi/recovery/x-ui.db \
  --root /opt/omsi-nodekit/ultra
```

Аудит выполняет `PRAGMA integrity_check`, `foreign_key_check`, сравнивает
имена таблиц, число строк и содержимое без вывода строк, UUID, ключей и
идентификаторов подписок. Ненулевой код возврата означает отличие или ошибку
валидации; он не означает автоматически, что backup непригоден.
Передавать только redacted JSON-отчёт, не полную базу и ownership JSON.
Ограничение аудитора: 100 000 строк в каждой таблице.

## Порядок полноценного испытания

1. Сохранить текущее описание ноды, версию 3x-ui/Xray, конфигурацию Nodekit
   и проверенный бэкап в зашифрованном архиве вне VPS. Отдельно сохранить
   `manifest.json`, `compose.yaml`, `Caddyfile.site`, `tunnel-*.json`,
   `pool-*.json`, `xhttp-routes.json`, `firewall-rules.json`, SSH keys/
   known_hosts и запись о фактическом Caddy source mount. Они могут содержать
   секреты и не должны попадать в git/issue.
2. Запустить read-only аудит и сравнить резервные копии с исходными данными.
3. Для первого destructive round-trip создать **одноразовую копию VPS или
   изолированную тестовую VM**. Не использовать боевую `ultra`.
4. На копии удалить только строго доказанные ресурсы Nodekit-owned 3x-ui:
   Compose service `panel` по точному файлу/проекту, её приватную DB/каталог,
   её точные правила UFW и SSH systemd services. Не удалять shared Caddy.
   Подготовить запасной SSH доступ перед очисткой.
5. Восстановить ту же версию панели с теми же портами/path, .db и приватными
   sidecar-файлами. Восстановить/проверить systemd SSH units и scoped UFW.
   В shared Caddy менять только строго принадлежащий Nodekit site block
   через ownership guard, после `caddy validate`; никакой глобальной замены.
6. Выполнить аудит восстановленной базы, затем `doctor`, настоящую HTTPS
   probe через каждый SSH exit, публичную проверку TLS/подписки и внешний IP
   с телефона. Зафиксировать отличия настроек и ошибок, в том числе
   сохранность сторонних контейнеров и сайтов.
7. Только после зелёной репетиции формировать отдельную автоматику
   `panel reset/restore` с explicit confirmation, dry-run, path/ownership
   guards, recovery snapshots и rollback. Не совмещать с общим Docker cleanup.

Частичное восстановление SQLite при работающем Caddy не является полным
восстановлением VPS. Код Nodekit в текущем PR преднамеренно не предоставляет
кнопку «удалить всю ноду».

## Выборочный импорт VLESS-клиентов из SQLite-снимка

Это **не** восстановление всей панели. Новая операция `client_import` может
выбрать клиентов из одной сохранённой базы 3x-ui и добавить их к существующему
VLESS inbound. Приоритет — неизменные **UUID и subId**: выданная ранее ссылка
`https://sub.example.com:2096/sub/<subId>` сохраняет свой идентификатор.
Чтобы старая URL-ссылка продолжала работать, DNS, Caddy и public subURI
на целевой панели должны соответствовать используемому домену и пути.

### Интерфейс

1. Перейди в «Бэкапы» → «Загрузить бэкап» (если .db ещё не сохранён)
   → «Клиенты». Альтернатива: нода → Inbound → «Из бэкапа».
2. Выбери резервный файл, исходный VLESS inbound и клиентов. В UI видны
   email, состояние и наличие сохранённых UUID/subId; сами ключи не раскрываются.
3. Выбери управляемую целевую ноду и существующий VLESS inbound. Нужен свежий
   отчёт обнаружения, соответствующий SSH-адресу ноды.
4. «Посмотреть план» → «Запустить операцию». До первого изменения создаётся
   приватный SQLite-снимок целевой панели `before-client-import-*.db`.
5. Проверь в 3x-ui клиентские записи и публичные ссылки **через URL подписки**;
   при переносе на XHTTP сначала настрой публичный Hosts endpoint.

### Защита и ограничения

- Для 3x-ui **3.11.0** источником являются нормализованные `clients` и
  `client_inbounds` таблицы, а не потенциально устаревшая копия в
  `inbounds.settings`. Старые базы без нормализованных таблиц читаются из
  `settings.clients`.
- Копируются UUID, subId, email, enabled, квоты, срок действия и некоторые
  настройки продления. Не импортируются счётчики использования, старые
  `clientHostRuleIds`, device HWID и связи с другими inbound.
  Подписочные зависимости из `client_external_links` можно перенести отдельно
  при включении галочки «Восстановить связанные подписки» (см. ниже).
  Для XHTTP без Vision очищается несовместимый `flow`.
- Старые общие `subId` адаптируются к уникальным аккаунтам 3x-ui 3.11:
  один детерминированно выбранный владелец сохраняет исходный публичный ID,
  остальные сохраняют UUID и получают стабильные отдельные `nk-...` ID.
  Владелец получает связанные HTTPS-подписки участников на **текущем публичном
  subURI целевой ноды**. Поэтому исходный адрес подписки группы по-прежнему
  выдаёт восстановленные профили; отдельно настрой DNS/домен/порт/путь старого URL.
  Эти обязательные связи создаются даже при выключенной галочке восстановления
  необязательных внешних ссылок из дампа. Публичный HTTPS-путь должен работать
  также с самой VPS; после импорта проверь его содержимое.
  Выбор владельца и ID выполняется по всему дампу, независимо от порядка выбора
  клиентов и inbound; повторное присутствие клиента в нескольких inbound
  не создаёт новую идентичность. В UI показан email владельца. Выбери его
  вместе с участниками или перенеси сначала из другого исходного inbound.
  При переносе частями старая подписка объединяет только уже перенесённых
  участников. Чужие существующие ссылки владельца сохраняются, циклы отклоняются.
- При конфликте email/subId/UUID с *другой* учётной записью **на целевой панели** импорт
  останавливается, существующая запись не заменяется. Если клиент уже
  привязан к этому же inbound и UUID+subId совпадают, операция пропускает его.
  Автоматическое слияние/прикрепление существующего клиента к другому inbound
  — **отдельная функция**, не входит в первый патч.
- За один запуск выбирается не больше 100 клиентов. В случае сбоя Nodekit
  пытается откатить только новые записи с прежними UUID+subId; исходный
  дамп, SSH-туннели, Caddy, Docker и остальные inbound не меняются.
  Изменения связанных подписок существующего владельца также компенсируются.
- Переход REALITY → XHTTP/TLS сохраняет UUID, но меняет транспорт и публичный
  endpoint. Старые статические `vless://` ссылки REALITY нужно обновить;
  клиенты с URL подписки должны загрузить новые профили. Старые серверные
  REALITY-ключи не копируются в XHTTP inbound.
- Новый сценарий тестируется на отдельном стенде/тестовом inbound до
  применения к действующей Москве.

### Восстановление агрегированных подписок из client_external_links

В версии 3x-ui 3.11.0 таблица `client_external_links` хранит дополнительные
источники конфигураций для аккаунта. `kind=subscription` означает, что
при выдаче подписки клиенту 3x-ui скачивает другой URL и **объединяет
полученные из него конфигурации**. Это не новый клиентский UUID и не новый
`subId`; это направленная связь владельца ссылки с другим источником.

Для иллюстрации: одна резервная база может содержать несколько HTTPS-ссылок
на подписки других клиентов этой же панели, например
`https://sub.example.com:2096/sub/<subId>`.
Количество владельцев/связей зависит от реальной базы. Перед переносом
необходимо проверять циклы, самоссылки и принадлежность URL, а не считать
их отсутствие заранее доказанным.

В мастере импорта включи «Восстановить связанные подписки».
Nodekit отобразит количество связей и зависимости только через внутренние
номера строк каталога, **без bearer URL или токенов**. При импорте владельца
ссылки также выбери всех связанных клиентов (кнопка «Добавить связанных»).
Они могут быть уже в целевой панели с **точно такими же** email, UUID и subId;
тогда повторно создавать их не нужно.

Порядок применения: validate source schema/subURI → проверить отсутствие
циклов, несовпадающих доменов и конфликтов клиентских ID → snapshot SQLite →
создать всех новых клиентов через Clients API → настроить связи через
`POST /panel/api/clients/:email/externalLinks` → проверить результат.
Последний endpoint заменяет **весь** набор ссылок клиента. Поэтому Nodekit
добавляет лишь отсутствующие ссылки и сохраняет прежние, не перезаписывая
несовпадающие записи, а при неудаче пытается откатить только собственные
изменения по точному снимку.

Автоматически допускаются только HTTPS URL внутри **того же публичного
адреса подписок**, соответствующие другому `subId` из исходного SQLite.
Произвольные внешние subscription URL и сырые share links не копируются
без отдельной явной операции: 3x-ui может обращаться к таким адресам из
серверной сети (опасность SSRF, циклов и перенаправлений).
`last_fetch_at` и `last_fetch_error` не переносим — это кэш состояния,
а не сама ссылка. Параметры `kind`, `value`, `remark`, `enable`,
`expiryTime` и `namePrefix` сохраняем.

**После восстановления** проверь `https://sub.example.com:2096/sub/<subId>`
для нескольких владельцев связей и убедись, что в результате появляются
составные VPN-конфигурации. При недоступности домена из самой VPS или Caddy
внутренние вложенные запросы могут не проходить; наличие строк в SQLite
само по себе не доказывает сетевую работоспособность.

Выбор Docker/native и Caddy независимо от источника SQLite, с чтением путей
выбранного бэкапа: [окружение восстановления](restore-targets.md).
Публичный вход: [доступ через Caddy](panel-access.md).
