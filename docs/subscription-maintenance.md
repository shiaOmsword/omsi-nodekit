# Nodekit — подписки, VLESS-клиенты и обслуживание серверного кэша

## Когда использовать

Все публичные URL ниже — примеры на зарезервированном домене `example.com`.
Реальные `subId`, узлы и домены в Git публиковать не следует.

После правки VLESS/XHTTP inbound, изменения Hosts или миграции клиента со старой
VPS новый Xray-маршрут может работать, а V2BOX показывать таймауты и обновлять
подписку с задержкой. Это **не обязательно** неисправность VPN: получение
подписки и измерение ping — разные действия. Hiddify/V2BOX могут кэшировать
DNS, URL и собственный набор профилей.

В Nodekit есть отдельная страница **«Подписки и ключи»**:

1. Выбери управляемую ноду и inbound. Если нет актуального отчёта, запусти
   «Обновить обнаружение».
2. На странице отображаются email, состояние и наличие subId клиентов.
   UUID и bearer subId намеренно остаются на VPS. Добавление, удаление и
   перенос из бэкапа используют существующие действия с preflight и snapshot.
3. «Проверить DNS и HTTPS»: агент на выбранной VPS считывает subURI 3x-ui,
   проверяет резолвинг настроенного домена, GET реального
   `https://sub.example.com:2096/sub/<subId>` **только** для выбранного клиента
   с TLS-верификацией и без HTTP-redirect, считает полученные proxy URLs,
   сообщает статус вложенных subscription ссылок.
4. Результат и предупреждения находятся в «Операции» / на этой странице
   в журнале последней проверки. **Токены, UUID и тело ответа не выводятся.**
5. Если всё хорошо, но клиент продолжает показывать старые конфигурации:
   проверь DNS A/AAAA для домена *VPN endpoint*, затем перезапусти/обнови
   мобильное приложение или пересоздай только подписку в нём. Сервер не
   умеет стирать кэш мобильного клиента.

## Три разных кэша

| Участок | Реальное поведение 3x-ui 3.11.0 | Нужен ли сброс |
| --- | --- | --- |
| Конфигурация inbound для подписки | 10-секундный in-memory TTL, панель сбрасывает сама при изменениях | Обычно нет |
| Вложенные `client_external_links` | 5-минутный in-memory TTL; при проблеме запроса может быть возвращён ранее загруженный результат | Только при доказанной необходимости |
| DNS/Caddy/browser/V2BOX/Hiddify | Собственные внешние кэши; TTL зависит от резолвера/клиента | Nodekit не управляет ими |

Исходники:
- `internal/sub/settings_cache.go` 3x-ui 3.11.0
- `internal/sub/external_subscription.go` 3x-ui 3.11.0

В **3x-ui 3.11.0 нет публичного API сброса кэша вложенных подписок**.
`Cache-Control: no-cache`, рефреш HTTP URL и
`server/restartXrayService` **не** гарантируют сброс in-memory кэша Go-панели.
Поэтому Nodekit не называет эти действия «очисткой».

## Принудительный сброс серверного кэша

Запускается **только вручную**: галочка-подтверждение → предпросмотр
опасной операции → «Перезапустить 3x-ui».

Перед изменением агент проверяет:

- На VPS выбрана управляемая Nodekit 3x-ui и текущий inbound fingerprint не
  поменялся.
- Есть корректный manifest и каталог базы внутри owned Nodekit проекта.
- Docker container действительно имеет **точные** Compose labels
  `com.docker.compose.project=<nodekit-project>` и
  `com.docker.compose.service=panel`, а его ID совпадает с обнаруженным.
- Контейнер запущен, перед рестартом создаётся SQLite snapshot
  `before-sub-cache-reset-*.db`.

Затем выполняется только:

```bash
docker restart --time 10 <verified-panel-container-id>
```

Агент ждёт локальный listener панели и проверяет fingerprint inbound.
Перезапуск выбрасывает **in-memory** кэши панели, но может кратко
прервать **все** действующие VPN-соединения этого 3x-ui (Xray ребёнок панели).
Ни shared Caddy, ни Docker daemon, ни SSH systemd units, ни UFW, ни DNS
не перезапускаются. Для native/чужой панели кнопка недоступна.

**Не запускать автоматически после каждой правки inbound**: штатный кэш
конфигурации короткий и уже инвалидируется самой панелью, а принудительный
перезапуск ухудшает доступность VPN. Рекомендованный сценарий после правки:
прочитать свежий inventory → проверить DNS/HTTPS → при явной проблеме
выбрать контролируемую очистку.

## При переносе VPS

Чтобы сократить период расхождения, снизь TTL DNS A/AAAA **заранее**
(60–300 сек, по возможности), не меняй публичный subURI
`https://sub.example.com:2096/sub/`, сохраняй subId при переносе клиентов
и оставляй старый ingress на переходный период, если VPS доступна.
Сбрасывать записи `known_hosts`, глобальные DNS-кэши ОС или Docker/Caddy
для проблемы V2BOX нельзя.
