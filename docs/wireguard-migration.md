# Перенос WireGuard и wg-easy в 3x-ui

Nodekit поддерживает перенос обычного WireGuard из согласованного SQLite-снимка
**wg-easy v15** в отдельный managed WG inbound 3x-ui. Источник определяется по
схеме базы, а не по имени файла. Импорт v14 `wg0.json` и AmneziaWG не поддерживается.
Секретные ключи не следует присылать в чат или журнал задания.

## Практический перенос wg-easy v15

### 1. Сделать согласованный снимок на старой VPS

Скопируй `tools/export_wg_easy.py` из этой версии Nodekit на Docker-хост wg-easy.
Скрипт использует только Python 3 и Docker CLI; Poetry на старой VPS не нужен.

```bash
sudo python3 tools/export_wg_easy.py \
  --container wg-easy \
  --output "$PWD/wg-easy-migration.db"
```

Вывод содержит только путь, образ и runtime-флаг `source_ipv6`. Например,
`source_ipv6: false` означает `DISABLE_IPV6=true`. Скрипт сверяет флаг с активным
`wg0.conf` и отклоняет AmneziaWG. Он находит Docker mount `/etc/wireguard`, снимает
базу через SQLite backup API (включая подтверждённые изменения из WAL), проверяет
целостность и создаёт файл с правами `0600`. При запуске через sudo владельцем
готового снимка становится вызвавший пользователь. Существующий файл не
перезаписывается. Сервисы, ключи, routing и firewall исходной VPS не меняются.

Не копируй только основной файл живой WAL-базы через `cp`/`docker cp`: последние
подтверждённые изменения могут оставаться в `wg-easy.db-wal`. Во время экспорта
не редактируй настройки панели, чтобы результат и проверенный runtime относились
к одному состоянию. Снимок содержит все таблицы, в том числе секреты самой панели;
переноси его по SSH и загружай в локальный Nodekit, без публикации в Git/чате.

### 2. Загрузить и проверить перенос

1. В **Бэкапы → Загрузить бэкап** загрузи `wg-easy-migration.db`.
2. На **новой** ноде выбери **Inbound → + WireGuard → Перенести WG из 3x-ui / wg-easy v15**.
3. Выбери снимок и исходный интерфейс. Проверь список клиентов и несовместимости.
4. Укажи `source_ipv6` из вывода экспорта. SQLite сохраняет IPv6-поля даже когда
   IPv6 был отключён в Docker environment; автоматически определить это из `.db`
   нельзя. Этот режим предназначен только для обычного WireGuard.
5. Укажи новый публичный IP/домен и UDP-порт. Сохраняй прежний внешний порт,
   если меняешь у клиентов только адрес. Прежний Endpoint показывается отдельно;
   он не подставляется вместо адреса новой VPS.
6. Просмотри план и запусти создание отдельного inbound. Перед изменениями
   сохраняется SQLite-снимок целевой панели. Данные повторно проверяются при
   preview, постановке задания и на целевой VPS. Оригинальный wg-easy `.db`
   остаётся доступен для скачивания в Nodekit; полное восстановление 3x-ui
   из этого файла отклоняется.

Локальный backend проверяет пары private/public через `cryptography` X25519;
несовпадающие пары отклоняются без замены ключей. Новых библиотек на VPS не нужно:
удалённый агент остаётся на стандартной библиотеке Python.

Импорт идёт через API 3x-ui, с проверкой сохранённых идентичностей, UDP listener
и существующим scoped rollback при ошибке. TCP-проверка не считается WG handshake.
Новая нода должна иметь настроенную выдачу HTTPS-подписок 3x-ui через Caddy.

### 3. Что именно переносится

| wg-easy v15 | 3x-ui / Nodekit |
| --- | --- |
| `interfaces_table.private_key` | WG `secretKey`, без генерации новой серверной пары |
| `clients_table.private_key/public_key/pre_shared_key` | Ключи peer и PSK; пустой/нулевой PSK остаётся отсутствующим |
| `ipv4_address`, `ipv6_address` | Серверные peer `allowedIPs` `/32`, `/128`; IPv6 только при выбранном включённом runtime |
| `persistent_keepalive` | `keepAlive`, включая ноль |
| `enabled`, `expires_at` | `enable`, абсолютный `expiryTime` в миллисекундах UTC |
| `name` | Сохраняется в `comment`; безопасное уникальное имя также становится `email` |
| Пробелы, кириллица, дубли в `name` | Исходное имя в `comment`, уникальный технический `wg-easy-<interface>-<id>` в `email` |
| `ipv4_cidr` | `subnetIp/subnetCidr` для дальнейшего выделения адресов |
| MTU, DNS | Общие настройки WG inbound, если исходные настройки совместимы |
| Внешний `user_configs_table.host/port` | Показывается как старый Endpoint; новый задаётся отдельно |

У wg-easy нет нативного `subId` 3x-ui: создаются **новые** идентификаторы аккаунтов
и подписок. Это не меняет WireGuard-ключи. Клиентские private keys не вычисляются
из public и не заменяются случайными; если private отсутствует, старый клиент
может продолжить работу, но повторная выдача его профиля невозможна.

Общие DNS/MTU 3x-ui и её native WG-профили не имеют точного соответствия всем
настройкам wg-easy. Поэтому импорт **останавливается**, если есть индивидуальные
DNS/MTU, split-tunnel `AllowedIPs`, сети за peer, статические серверные Endpoint,
клиентские hooks, нестандартные серверные hooks, особая routing table или
включённая клиентская фильтрация wg-easy. DNS внутри прежней WG-подсети тоже
требует отдельного переноса сервиса, поэтому такой источник блокируется.
Сами значения hooks/команд не показываются в каталоге и не исполняются.

Стандартные NAT/INPUT/FORWARD hooks wg-easy распознаются и заменяются моделью
маршрутизации Xray. Учётные записи админов wg-easy, пароли, TOTP, сессии, метрики,
одноразовые ссылки и runtime sing-box не импортируются в другую панель. Они
сохраняются в полном исходном снимке, если были частью SQLite. Это перенос
совместимых настроек WireGuard, а не побайтовое восстановление старого приложения.

### 4. Проверить одного клиента и переключить Endpoint

На копии существующего клиентского профиля меняй только `Endpoint` на новый
IP/домен и порт. Серверный public key, клиентский private key, PSK и адреса
должны остаться прежними. Проверь IPv4/IPv6, DNS, UDP, внешний IP, reconnect и
обычную работу приложений с внешнего устройства.

Зарубежный выход выбирается отдельно существующим маршрутом Nodekit для WG
inbound. Импорт не копирует старые sing-box/nftables правила и не обещает
эквивалентность native L3/site-to-site сети kernel WireGuard userspace Xray.
Проверку ping/ICMP нельзя подменять проверкой TCP/UDP или наоборот.

Если у клиентов записан **буквальный старый IP**, смена DNS и выпуск новой
подписки не обновят уже импортированные профили WireGuard. Для каждого такого
устройства требуется правка Endpoint/повторный импорт либо отдельный временный
UDP relay со старого IP на новый с корректным возвратным путём. Автоматическая
настройка relay в адаптер не входит. Старую ноду сохраняй до проверки перехода.

## Ключ, Endpoint и подписка — разные вещи

| Объект | Назначение |
| --- | --- |
| Клиентская пара private/public | Идентичность клиента при аутентификации |
| Серверная пара private/public | Серверная идентичность, которой доверяет клиент |
| `Endpoint = wg.example.com:51820` | Куда клиент посылает UDP; домен разрешается в IP |
| URL подписки, например `https://sub.example.com/sub/...` | Откуда поддерживающий подписки клиент загружает профиль |

Ключ не привязан криптографически к публичному IP или домену. У ключа нет
DNS-записи или серверного «редиректа». Endpoint и место выдачи конфигурации
могут меняться отдельно. Перенос подписки не является push-командой уже
работающему WG-туннелю.

Обычное приложение WireGuard после импорта `.conf`/QR не превращает профиль
в автоматически обновляемую подписку. В клиентах с поддержкой WG-подписок
это зависит от формата, наличия подписки и политики обновления. После
обновления может потребоваться переподключение профиля.

## Когда можно сохранить действующие клиентские конфиги

На новом сервере должны сохраниться:

- **Тот же серверный private key**, чтобы клиент по-прежнему видел ожидаемый
  server public key. Новой случайной серверной пары для прозрачного переноса
  недостаточно.
- Public keys клиентов, PSK при их использовании, клиентские адреса и
  соответствующие серверные allowedIPs; адреса peers не должны пересекаться.
- Доступность того же внешнего UDP-порта. Сохранить и проверить маршрутизацию,
  MTU, DNS и доступ к нужным ресурсам.
- Домен Endpoint, если он уже записан у клиента, с переносом DNS на новую VPS.

Клиентский private key для работы старого клиента остаётся на самом клиенте;
на сервере достаточно его public key и соответствующих настроек. Но чтобы
**выдавать тот же полный клиентский профиль из новой подписки**, нужны
исходные клиентские private keys. Их невозможно вычислить из public key.
Если экспорт wg-easy содержит их, будущий импорт может сохранить их без
перевыдачи. Если нет, существующее подключение и повторная выдача конфига —
разные по возможностям сценарии.

Если на целевой 3x-ui уже есть WG inbound с другим server key, старые клиенты
wg-easy не начнут ему доверять от одного добавления peers. Для сохранения
старой идентичности нужен отдельный inbound либо согласованное изменение
существующего. Если наружный порт уже занят другой WG-идентичностью,
одного DNS недостаточно: нужен отдельный адрес, согласованный перенос порта
или обновление клиентских Endpoint.

Особенно проверить DNS: если старый профиль использовал `10.8.0.1` как DNS
wg-easy, перенос ключей в userspace Xray не создаёт там прежний DNS-сервис.
Нужно обеспечить эквивалентную обработку DNS или обновить клиентский профиль.
Handshake без работающего DNS не означает успешного переноса.

## DNS и клиенты, которые не успели

Домен удобнее фиксированного IP, но DNS TTL не гарантирует мгновенного
переключения активного WireGuard. Разные реализации по-разному обновляют
Endpoint; обычному конфигу может потребоваться переподключение/повторное
разрешение имени. В wireguard-tools существует отдельный reresolve-dns helper
именно для обновления Endpoint после изменения DNS. Протокольный endpoint
roaming по аутентифицированным пакетам не равен регулярному DNS polling.

Практический переход:

1. Сохранить полный приватный бэкап wg-easy и сверить его формат/версию.
   Не удалять исходный сервер и не генерировать новые серверные ключи заранее.
2. Подготовить совместимый inbound на новом сервере, проверить одного клиента
   отдельно: handshake, IPv4/IPv6, внешний IP, DNS, UDP и переподключение.
3. Если Endpoint — домен, перенести DNS (проверить A и AAAA) и дать клиентам переподключиться.
   При необходимости обновить также домен выдачи подписок и ссылки аккаунтов.
4. На период перехода сохранить старый UDP Endpoint доступным. При подходящей
   инфраструктуре он может временно пересылать UDP на новый сервер с корректным
   возвратным путём/NAT. Это отдельная сетевая настройка, не HTTP redirect и
   не обычный Caddy reverse_proxy; те же серверные ключи всё равно необходимы.
5. Проверять активность peers на обоих концах и отдельно учитывать офлайн
   клиентов. Нулевая активность на старой VPS не доказывает, что все профили
   обновились: часть людей могла долго не включать VPN.

Если у клиента записан **старый буквальный IP**, смена DNS ему не поможет.
После полного отключения этого адреса такой профиль не заработает без
обновления Endpoint либо сохранения/переноса старого IP или совместимого
UDP relay. Нельзя одновременно выключить старый адрес и гарантировать
доступ никогда не обновлявшемуся клиенту с этим адресом.

## Проверка реализации

Отображение полей сверено с wg-easy v15.5.0 (`99970aaa`) и 3x-ui v3.11.0
(`c621ba9`). Адаптер проверяет обязательные поля схемы v15 и не определяет
совместимость по плавающему Docker tag `:15`. Локальные проверки используют
синтетические SQLite-снимки, API-сценарии и изолированный SSH bundle.
Реальная интеграция с панелью и внешний WG handshake на VPS требуют отдельной
проверки перед массовым переносом. CI не доказывает работоспособность внешнего UDP.
