# Адаптивное развёртывание нод

Чтение inbound/клиентов, диагностика цепочки подписок, первый клиент и
изменение настроек установленной панели описаны в [subscriptions.md](subscriptions.md).

`panel.installation` выбирает установку для обнаружения; новый блок
`deployment` описывает желаемое развёртывание. Старые YAML без него
продолжают работать через прежний Docker-сценарий.

## Порядок работы в панели

1. Сохрани SSH-конфигурацию и запусти проверку окружения.
2. Открой **Заполнить по отчёту**: выбери найденную панель либо роль новой ноды.
   Для новой ноды при необходимости выбери конкретный общий Caddy и нажми
   **Применить и сохранить**. Это сохраняет локальную конфигурацию.
3. Открой **Параметры установки**: выбери native/Docker, способ подключения
   Caddy и добавь нужные inbound. Для Restore сначала выбери бэкап.
4. Сохрани параметры, проверь YAML и открой план Fresh или Restore.
   Запуск выполняется существующей кнопкой подтверждения конкретного плана.

Подстановка сохраняет ноду локально, но не меняет VPS. Наблюдённые порты и пути
копируются только из выбранной панели; значения, помеченные в отчёте как
upstream defaults, не подменяют YAML. SSH-секреты черновика сохраняются.
Отчёт проверяется по node ID, адресу и порту SSH. Старые отчёты без этих
метаданных требуют повторного обнаружения.

## Выходная нода

Роль `exit` подходит для GB/NL/другого зарубежного сервера. Базовый выбор —
Docker + Caddy в новом профиле интерфейса; для выделенного SSH-выхода можно
явно выбрать native без Caddy, как в примере ниже. Регион не
определяется по IP: роль задаётся явно.

```yaml
id: exit-gb
name: GB exit
ssh:
  host: 203.0.113.20
  user: omsi
  identity_file: ~/.ssh/exit_gb
  sudo: true
  # sudo_password_env: NODEKIT_EXIT_SUDO_PASSWORD
panel:
  installation: managed
  port: 2053
  base_path: /nodekit/
  subscription_port: 2097
  subscription_path: /sub/
caddy:
  enabled: false
deployment:
  role: exit
  panel_runtime: native
  caddy_mode: none
  inbounds:
    - name: moscow-ssh
      port: 8443
      listen: 127.0.0.1
      server_name: www.example.com # замени на проверенный REALITY target/SNI
      target_port: 443
tunnels: []
```

Native поддерживает Linux amd64/arm64 и фиксированный релиз 3x-ui **3.11.0**.
Архив с официального GitHub проверяется по зафиксированному SHA256; symlink,
hardlink и пути `..` запрещены. Бинарник, БД и systemd unit принадлежат ноде:

- `/opt/omsi-nodekit/exit-gb/runtime/`
- `/opt/omsi-nodekit/exit-gb/db/x-ui.db`
- `omsi-exit-gb-panel.service`

Глобальная установка `/usr/local/x-ui` не заменяется. Docker для native
без нового Docker Caddy не нужен. Панель остаётся на loopback, а пароль
сохраняется на VPS в `credentials.json` с правами `600`.

```bash
ssh -i ~/.ssh/exit_gb -L 2053:127.0.0.1:2053 omsi@203.0.113.20
# Локальная панель: http://127.0.0.1:2053/nodekit/
```

При других портах или base_path подставь значения своей ноды.

## Docker и пакеты

`panel_runtime: docker` использует фиксированный `panel.image` и host
networking, поэтому loopback SSH-туннелей имеет тот же смысл, что на хосте.
`caddy_mode: docker` создаёт собственный Docker Caddy; он совместим и с
native 3x-ui. Docker сам по себе не требует Caddy.

`install_docker: true` явно разрешает установить отсутствующий Docker через
`apt-get`: пакеты `docker.io` и `docker-compose-v2` на Ubuntu/Debian.
Compose должен присутствовать в репозиториях ОС. Уже установленный Docker
не заменяется; неработающий существующий Engine не запускается молча.
Установленные пакеты не удаляются при последующем сбое установки панели.
Python 3.11+ требуется до запуска удалённого агента; bootstrap Python пока
отсутствует. Новый native Caddy не устанавливается этим сценарием.

## Общий Caddy без существующей панели

Выбери `caddy_mode: existing`, `caddy_id` из отчёта и
`caddy.enabled: true`. Подстановка выбирает адрес подписок:

- native Caddy или Docker host networking: `127.0.0.1`;
- Docker bridge: единственный найденный gateway сети. Подписки слушают
  этот интерфейс хоста. Панель остаётся на loopback, кроме явно включённого
  [защищённого доступа через bridge Caddy](panel-access.md): тогда ей нужен
  тот же приватный gateway.

Сети контейнера сохраняются. В bridge HTTPS-порт публикуется с одинаковым
номером снаружи/внутри, например `443:443`. При включённом согласовании
Nodekit добавляет недостающие публикации через минимальный Compose override;
сервис Caddy кратковременно пересоздаётся. При отключённом согласовании
публикации должны быть подготовлены вручную. При нескольких gateways
значение не угадывается. См. [управление сетью](network-management.md).

Для нового сайта задай отдельный домен в `caddy.domain`. REALITY SNI и домен
подписок независимы. Если Caddy занимает 443, выбери для inbound другой
свободный порт, например 8443.

Перед записью проверяются активный экземпляр, доступность Caddyfile и
локального admin API `127.0.0.1:2019`, совпадение файла с активной
JSON-конфигурацией, hostname и порты. JSON-конфиг, `--resume`,
отключённый/нестандартный admin API или неподдерживаемая топология вызывают
отказ. Для чтения admin API Docker Caddy нужен `wget` внутри контейнера.

Исходный файл сохраняется как `Caddyfile.original` в закрытом каталоге ноды.
Затем добавляется отдельный сайт, выполняются validate/reload и проверка
принятой конфигурации. Сохраняется inode для Docker bind mount отдельного
файла. При ошибке возвращается точное исходное содержимое и выполняется
reload. Конкурентное редактирование останавливает перезапись. При изменении
только сайта общий Caddy получает reload. Если нужно добавить Compose-публикации,
его контейнер кратковременно пересоздаётся, прерывая все сайты.

Публичные DNS, ACME и HTTPS проверяются отдельно с внешнего клиента:
успешный reload их не доказывает.

## Inbound и Москва

При Fresh явно заданные VLESS/REALITY inbound создаются через локальный
аутентифицированный API 3x-ui 3.11.0. UUID, X25519-ключи и short ID генерируются
на VPS. Проверяются сохранённые параметры и TCP-порты после запуска Xray.
Конфликтующие inbound не заменяются, существующие ключи не вращаются.
Restore не создаёт inbound из списка и сохраняет идентичности из БД.

Файл `/opt/omsi-nodekit/<node-id>/tunnel-connections.json` (`600`) содержит
публичный REALITY key, UUID, SNI, short ID и шаблоны Xray outbound для Москвы.
Приватный REALITY key остаётся в БД панели. Локальный API token хранится в
отдельном файле `api-token` (`600`).

Согласуй свободный локальный порт Москвы в outbound с `tunnels.local_port`
или SSH `-L`. Значения 15443 и следующие в экспорте — примеры. SSH forwarding
должен вести на `127.0.0.1:<exit_port>` зарубежного сервера. Отдельные SSH-ключ
и known_hosts для Москва → exit подготавливаются на Москве.

Fresh выходной ноды не меняет другую, московскую панель. В ней подготовь
исходный VLESS/REALITY outbound вручную; затем [мастер SSH-выхода](ssh-egress.md)
создаст его loopback-копии, балансировщик и выбранный маршрут через API.
После применения нужна проверка запроса через весь маршрут; открытый
inbound-порт не подтверждает прохождение VPN-трафика.

## Отказы и проверки

Fresh/Restore прекращаются при существующей панели, занятом каталоге,
порте или unit, а также при ошибках инвентаризации. Порты проверяются по TCP
и UDP с учётом адреса и конфликта IPv6 dual-stack wildcard. Перед запуском
адреса проверяются повторно; это не постоянная резервация порта.

При сбое останавливаются только созданные сервисы Nodekit; БД и файлы
сохраняются для диагностики. Существующие сервисы и каталоги не удаляются.

Покрытие: тесты API и подстановки, конфликтов, native/Docker rendering,
отката Caddy, архива, приватности ошибок/экспорта и frontend. На Linux
выполнены дополнительные прогоны настоящих 3x-ui 3.11.0 и Caddy 2.10.2:
создание REALITY через API с запуском Xray, добавление HTTP-маршрута к
действующему Caddy и точный откат. Эти локальные прогоны не подтверждают любую
пользовательскую топологию. Для своей VPS отдельно проверь SSH, публичный
DNS/TLS и полный клиентский маршрут.
