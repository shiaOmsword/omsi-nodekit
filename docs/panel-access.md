# Доступ к 3x-ui через Caddy

**Нода → Обзор → Доступ к 3x-ui → Настроить доступ**. Нужны активная managed
панель Nodekit, свежий отчёт и настроенный Caddy. Отдельный Nginx не требуется. Режим basic_auth требует Caddy 2.8+;
проверенная версия — 2.10.2.

## Режимы

- **Только SSH** — управляемый публичный маршрут панели отсутствует.
- **Дополнительный логин и пароль** — Caddy проверяет HTTP Basic Auth по HTTPS,
  затем открывается обычная авторизация 3x-ui. Уже существующая сессия панели
  сохраняет своё обычное поведение. Пароль хешируется bcrypt в браузере;
  исходный пароль не отправляется локальному backend Nodekit, не сохраняется
  в YAML, плане или журнале. Caddy получает только хеш в конфигурации.
- **Только разрешённые IP / сети** — список IPv4, IPv6 или CIDR. При запрете
  возвращается HTTP 403. Заголовок X-Forwarded-For сам по себе не даёт доступ.
  За CDN/дополнительным прокси нужен отдельный согласованный профиль доверия:
  этот режим проверяет непосредственный адрес соединения с Caddy.

Пароль Caddy отличается от пароля 3x-ui. Пустое поле нового пароля сохраняет
имеющийся хеш; отключение режима удаляет его из желаемого конфига.
Для смены закешированных браузером Basic Auth credentials может понадобиться
закрыть окно браузера. Публичный 3x-ui API с Bearer-токеном не получает отдельного
исключения из Basic Auth: Nodekit обращается к приватному API напрямую.

Защита относится к пути панели и варианту без завершающего `/`. Публичный
путь подписок обрабатывается отдельно, первым. Поэтому корневой путь панели
`/` допустим, а путь панели внутри публичного префикса подписок — нет.
Например, `/sub/admin/` при `subscription_path: /sub/` отклоняется.
Существующие XHTTP сайты сохраняются. Внутри защищённого panel handler Basic
Authorization не передаётся в 3x-ui; session cookies сохраняются.

## Применение и резервный вход

Сохранение настроек открывает существующий план `configure` или `attach_caddy`.
Нужно отдельно запустить этот план. До применения сохранённый YAML не считается
состоянием VPS. Панель/Xray перезапускаются; подключения могут прерваться.

Собственный standalone Docker Caddy подключается через прежний механизм
`attach_caddy`: проверяются его файлы, образ, Compose ownership и команда.
Только для этого контейнера может включиться локальный admin API и произойти
перезапуск. Общий Caddy сохраняет чужие сайты; сверяются файл, adapted config
и фактически загруженная конфигурация. Перед изменением есть приватный бэкап;
при сбое выполняется scoped rollback.

При host networking или native Caddy панель остаётся на `127.0.0.1`.
Для общего Caddy в Docker bridge защищённая панель слушает приватный host
gateway из `deployment.subscription_bind`. Публичный wildcard listener
`0.0.0.0` не создаётся, Docker-публикация порта панели не добавляется.
Для активного управляемого UFW добавляется правило только от нужного bridge
к приватному адресу/порту панели. API, readiness и диагностика используют
тот же адрес. При отключении публичного входа панель возвращается на loopback.

В обзоре показана команда SSH-forward к фактическому адресу backend. Она
обходит Caddy и его IP/password gate; обычная авторизация 3x-ui остаётся.
Использовать свой SSH-ключ/профиль и свободный локальный порт. После изменения
bridge/gateway старый туннель к `127.0.0.1:2053` может потребовать другого
адреса назначения — копировать актуальную команду из отчёта. Если SSHD
ограничен PermitOpen, в нём должен быть разрешён этот приватный адрес.

Кнопка открытия панели доступна при совпадении сохранённого/обнаруженного
профиля. Это не проверка внешнего DNS/TLS и доступности с конкретного IP.
После применения проверить в отдельном окне: запрос без пароля/с неверным
паролем, успешный вход, доступ с разрешённого/запрещённого IP, подписку и
резервный SSH-вход. Не включать IP-список из текущего меняющегося адреса,
не имея рабочего SSH-доступа.

## Проверка реализации

Существующие проверки приложения дополнены временной локальной пробой на
официальном Caddy 2.10.2: Basic Auth 401/200; удаление Basic Authorization
перед panel upstream при сохранении cookies; 403 для запрещённого IP;
поддельный X-Forwarded-For не обходит запрет; подписки доступны отдельно;
корневой panel path работает; отключённый маршрут возвращает 404.
Проба использует временные HTTP backends и self-signed TLS, не VPS.

Источники: [Caddy basic_auth](https://caddyserver.com/docs/caddyfile/directives/basic_auth),
[remote_ip matcher](https://caddyserver.com/docs/caddyfile/matchers#remote-ip),
[bcrypt.js](https://github.com/dcodeIO/bcrypt.js).
