# Inbound, UFW и общий Caddy

## Применение патча

Обнови Nodekit и выполни обнаружение ноды. Во вкладке **Inbound** доступны
редактирование имени, порта и REALITY SNI, удаление и проверка трафика.
Каждое действие сначала готовит план; запуск выполняется отдельной кнопкой.
Удаление также требует флажка подтверждения и удаляет клиентов inbound.

Изменения поддерживаются для активной панели Nodekit 3.11.0 с исходным
manifest и принадлежащей ей SQLite. Перед операцией сохраняется приватный
`before-inbound-*.db` на VPS. Проверяется fingerprint обнаруженных настроек
и повторно читается конфигурация перед записью. API сохраняет клиентов,
UUID, ID подписок, настройки и ключи REALITY. При смене SNI меняются
serverNames и hostname target; target-порт остаётся прежним. 3x-ui сама
обновляет автоматически созданный tag при смене порта и переносит ссылки
маршрутизации. После редактирования обнови подписку в клиенте.

`inbound-identities.json` связывает шаблоны создания с ID: повторный
`configure` не восстанавливает удалённый inbound и не перезаписывает
отредактированный. Чтобы создать новый, задай новое имя шаблона. Это
реестр создания, а не синхронизация произвольных изменений YAML с панелью.

## Firewall

В параметрах ноды по умолчанию включено **Настраивать правила UFW**
(`deployment.manage_ufw`). Изменения разрешены только при активном UFW;
Nodekit не включает, не сбрасывает и не меняет его политики. Если UFW
установлен, но его состояние не прочитано, операция останавливается.

Создание/редактирование открывает публичный TCP-порт VLESS перед запуском.
Loopback inbound не публикуется. Для подписок добавляются TCP 80 и
HTTPS-порт Caddy; Docker bridge → HTTP backend разрешается только для
обнаруженных subnet, gateway, интерфейса и внутреннего порта. Backend 2097
не открывается всему интернету. Правила имеют комментарий `nodekit:<id>:…`
и приватный реестр `firewall-rules.json`.

После смены порта/удаления неиспользуемые правила Nodekit удаляются. Если
порт занят другим listener/inbound/Caddy, разрешение сохраняется. Старое
ручное правило сохраняется, пока оператор явно не выберет его удаление в
модалке; удаляется только точное публичное TCP-разрешение старого порта,
без диапазонов, профилей и ограничений по subnet. При сбое редактирования
восстанавливаются прежняя конфигурация и изменения UFW этой операции.
Уже выполненное удаление клиентов не отменяется автоматически; snapshot
сохранён для явного восстановления.

`check` и `doctor` читают UFW, его политики и правила, показывают отсутствие
разрешений/публикаций и расхождения subURI, subListen, subPort, subEnable,
незаполненные REALITY SNI/target. Правило UFW не доказывает внешний доступ:
firewall провайдера и обход UFW публикациями Docker требуют отдельной
проверки с другого устройства. Проверка правил охватывает IPv4; IPv6
правила отображаются, но не используются как доказательство IPv4-доступа.

## Публикации общего Docker Caddy

**Добавлять недостающие порты общего Caddy**
(`deployment.manage_caddy_ports`) добавляет только недостающие TCP
`80:80` и `<HTTPS>:<HTTPS>`. Например, публичный 2096 остаётся портом
Caddy, а внутренний 2097 — HTTP-сервером 3x-ui.

Нужны Compose labels с исходным проектом, сервисом, рабочим каталогом,
списком файлов и config-hash. Nodekit сверяет эффективный Compose с
работающим контейнером и сохраняет исходные файлы. Создаётся минимальный
`compose.nodekit-<id>.ports.yaml` в рабочем каталоге проекта; другие
параметры сервиса и остальные сервисы не меняются. Перезапускается только
этот сервис с `--no-deps --no-build --pull never`. **Все сайты этого
Caddy кратковременно прерываются при пересоздании контейнера.**

Изменённые исходники, чужой override, произвольное remapping, недоступная
Compose metadata или занятый порт вызывают отказ. Пользовательские
env/CLI overrides не угадываются. Если автоматический режим не подходит,
выключи его, добавь публикацию вручную и повтори обнаружение. При сбое
восстанавливается только собственный override; чужие изменения не
перезаписываются. Последующие ручные команды Compose должны учитывать
этот override через `-f`, иначе дополнительные публикации исчезнут.

## Клиент принят, а сайты не отвечают

Открытый 8443 и access log подтверждают только приём соединения. Тег вроде
`From_MSK_inbound-ultra-ru` может принадлежать любому протоколу. Во вкладке
**Сеть** показаны фактические outbound protocol, default outbound,
inboundTag → outboundTag/balancer и отсутствующие ссылки. Полные JSON,
адреса удалённых proxy, UUID и пароли не экспортируются.

1. Запусти **Сеть → Диагностика**: прямой IPv4 HTTPS с VPS к example.com
   и www.google.com проверяет DNS/TCP/TLS и HTTP-ответы.
2. Запусти **Inbound → Проверить трафик** для TCP/raw VLESS/REALITY.
   Временный loopback SOCKS/Xray-клиент использует существующего
   включённого клиента и настоящий inbound с его routing. Сравниваются
   прямые и проксированные HTTP-коды, время, число полученных байт.
   Конфигурация с секретами удаляется, временный процесс завершается
   даже при ошибке. Пробный трафик учитывается у клиента.
3. Прямой HTTPS работает, inbound нет — исследуй выбранный outbound,
   routing, REALITY, flow и DNS Xray. Оба работают, устройство нет —
   проверь импортированный адрес/порт/SNI, flow, ключ, MTU и внешний
   участок. Ни один не работает — сначала выход/DNS/firewall VPS.

Эта проба не проверяет внешний маршрут устройство → VPS, UDP или MTU.
Маршруты, finalRules, DNS и политики UFW автоматически не переписываются.
Для обычного VLESS прямой выход через freedom не требует включать
ip_forward или разрешать все routed-пакеты в UFW.
